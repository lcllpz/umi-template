**首次传输字节时间**（TTFB）是 Web 性能的核心指标，它`通常出现在其他关键用户体验指标（如首次内容绘制 FCP 和最大内容绘制 LCP）之前`。TTFB 越高，用户看到页面内容的时间就越长，从而影响整体体验。

为确保大多数用户（第 75 百分位）能在“良好”阈值内实现 FCP，建议服务器尽可能快速响应导航请求。一般来说，网站应将 TTFB 控制在 0.8 秒以内。

![20250725120749](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250725120749.png)

良好的 TTFB 值不超过 0.8 秒，不良的 TTFB 值大于 1.8 秒。

## 什么是 TTFB

`TTFB（Time to First Byte）` 是一个性能指标，用于衡量从发出请求到接收到服务器返回的第一个字节所经历的时间。

![20250725121320](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250725121320.png)

网络请求阶段及其相关时间的示意图。TTFB 用于衡量 `startTime` 和 `responseStart` 之间的经过时间。

`TTFB（Time to First Byte）` 是衡量从浏览器发起请求到接收到服务器响应第一个字节所经历的总时间。它包括以下几个阶段：

1. 重定向时间（如果有）

2. Service Worker 启动时间（如果适用）

3. DNS 解析时间

4. TCP 连接和 TLS 协商时间

5. 请求发送与服务器响应首字节返回时间

降低 TTFB 的关键在于缩短连接建立时间和减少后端处理延迟，从而加快整体页面加载速度。

## 如何衡量 TTFB

在优化 TTFB 之前，应先评估它对用户实际体验的影响。建议优先参考真实用户数据（Field Data），因为 TTFB 会受到重定向等因素的影响，而这些延迟在实验室测试中通常会被忽略——实验室工具往往只测量最终页面的响应时间。

PageSpeed Insights 是一个实用工具，可同时提供来自 Chrome 用户体验报告（CrUX）的真实数据，以及基于 Lighthouse 的实验室评估，帮助您全面了解 TTFB 的表现和优化方向。

### 🧭 使用 Server-Timing 衡量后端性能瓶颈

`Server-Timing` 响应头允许你在浏览器中细化地查看后端处理耗时，包括数据库查询、服务器渲染、磁盘 I/O、CDN 缓存命中等。

该标头结构灵活，支持自定义名称（如 `db`、`ssr`）、时长（`dur`）和描述（`desc`），多个项之间用英文逗号分隔。

如下格式所示：

```
Server-Timing: db;desc="Database";dur=121.3, ssr;desc="Server-side Rendering";dur=212.2
```

---

### ✅ Node.js（Express）实现示例：

```js
const express = require("express");
const app = express();

app.get("/", async (req, res) => {
  const startDb = process.hrtime.bigint();

  // 模拟数据库查询
  await new Promise((resolve) => setTimeout(resolve, 120));

  const endDb = process.hrtime.bigint();
  const dbDuration = Number(endDb - startDb) / 1e6; // 转换为毫秒

  // 设置 Server-Timing 响应头
  res.set("Server-Timing", `db;desc="Database";dur=${dbDuration.toFixed(2)}`);

  res.send("<h1>Hello, world!</h1>");
});

app.listen(3000, () => {
  console.log("Server running on http://localhost:3000");
});
```

## 优化 TTFB 的方法

优化 TTFB 的最大挑战在于：虽然前端技术（HTML、CSS、JavaScript）相对统一，但后端架构差异巨大。不同的服务器框架、数据库和技术栈有各自的优化方法。

因此，本指南将聚焦于适用于大多数后端架构的通用优化策略，而非特定技术的细节。

### 📦 针对具体平台的优化建议

网站所使用的平台对 TTFB 有显著影响。例如，WordPress 的性能可能受插件数量、质量以及主题选择的影响；其他平台也存在类似情况，尤其是在经过定制后。

建议参考所用平台的官方文档，结合特定供应商的优化建议，来补充本文中的通用策略。此外，Lighthouse 的“缩短服务器响应时间”审核中也提供了一些与特定技术栈相关的优化提示，可供参考。

### ☁️ 托管，托管，还是托管

在考虑其他 TTFB 优化方法之前，优先评估你的托管服务。托管质量直接决定了服务器是否能及时响应用户请求。

对于静态页面较多、访问量较低的小型网站，共享托管服务可能已足够。配合本文提供的优化技巧，也能在一定程度上缩短 TTFB。

但如果你的网站涉及：

- 个性化内容

- 数据库查询

- 高并发用户访问

那么托管服务的性能将对 TTFB 产生关键影响。

选择托管服务时需关注：

- 内存分配是否充足？ 内存不足会导致服务器过载，拖慢响应速度。

- 后端栈是否及时更新？ 语言运行时、HTTP 引擎、数据库等底层技术的更新会带来性能提升。选择注重维护更新的服务商至关重要。

- 是否允许自定义？ 如需高级配置权限（如访问服务器配置文件），可考虑使用自建实例或云服务。

如果想了解当前托管服务的真实 TTFB 表现，可以访问[ismyhostfastyet.com](https://ismyhostfastyet.com)查看具体的表现：

![20250725135654](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250725135654.png)

若我们在使用优质托管的前提下仍遇到 TTFB 偏高的问题，那可能意味着当前服务商无法满足你的性能需求，需要重新评估和选择。

### 🌍 使用内容分发网络（CDN）

CDN 是提升 TTFB 的常见手段，原因很简单：即使后端优化得很好，远距离用户仍可能因为网络延迟而体验缓慢。

CDN 通过在全球部署的“边缘服务器”缓存资源，将内容分发到离用户更近的节点，从而显著降低 TTFB。

CDN 通常集成高性能 DNS 服务，并支持现代协议如 HTTP/2 和 HTTP/3，可实现更高效的传输。
其中，HTTP/3 基于 UDP，能避免 TCP 的队头阻塞问题。结合 TLS 1.3，还能显著减少连接延迟，加快首字节到达时间。

CDN 的高级功能如 Edge Workers 可在边缘服务器处理请求、缓存或重写响应，减轻后端压力。它还支持自动压缩静态资源，并优化动态内容压缩，避免因配置错误导致响应变慢。

CDN 的配置成本因平台而异，从简单开关到复杂集成都有。但如果我们尚未启用 CDN，它应是优化 TTFB 的首要步骤之一。

### 🗂️ 缓存内容对 TTFB 的影响

使用 CDN 时，只要配置了合适的 `Cache-Control` 标头，内容就可以缓存在更靠近用户的边缘节点，从而显著降低 TTFB。虽然个性化内容无法缓存，但如果所有请求都回源，CDN 的优势就会大打折扣。

![20250725140602](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250725140602.png)

即使缓存时间很短，也能显著改善高流量网站的性能——首位访问者触发回源，其他用户则可直接从缓存中获取内容。部分 CDN 还支持“缓存失效”，实现 长缓存 + 实时更新 的平衡。

不过要注意，唯一的查询参数可能导致 CDN 误判为不同内容，从而绕过缓存。使用参数进行分析时应谨慎配置缓存策略。

缓存虽然能显著提升性能，但也可能掩盖后端响应缓慢的问题，导致 TTFB 测试结果失真。访问量低或内容较旧的页面可能未被缓存，导致 TTFB 偏高；虽然延长缓存时间可缓解此问题，但也增加了内容过时的风险。

尽管如此，缓存命中仍能有效减轻数据库等后端压力，提升整体系统响应效率。

### 🔁 避免多次重定向，降低 TTFB

重定向是导致 TTFB 升高的常见原因。每一次重定向都会增加导航延迟，连续重定向（即重定向链）则会显著放大这一影响，特别是在通过广告或邮件吸引流量的场景中更为严重。

优先清除同源重定向，特别是那些触发 `301` 或 `302` 状态码的站内链接。常见原因包括链接未使用 `https://`（浏览器默认使用 `http://` 并触发重定向），或因尾部斜杠不一致导致路径跳转。

跨源重定向（如短链接服务）通常不易控制，但应避免多个跳转链接串联使用。确保提供给广告平台或邮件订阅用户的链接直接指向最终页面。

从 http 到 https 的重定向会增加 TTFB，建议使用 `Strict-Transport-Security (HSTS)` 标头，让浏览器自动以 HTTPS 访问，避免多余跳转。

部署稳定后，还可以将网站加入 [HSTS 预加载列表](https://developer.mozilla.org/zh-CN/docs/Web/HTTP/Reference/Headers/Strict-Transport-Security#preloading_strict_transport_security)，进一步提升首次访问速度。

### 🚀 将 HTML 标记流式传输到浏览器

浏览器支持流式解析 HTML，这意味着服务器无需等待完整页面生成，可以边生成边发送内容，从而显著降低首屏渲染延迟，特别适用于页面体积较大的场景。

为实现流畅的标记流式传输，关键是确保后端尽快开始输出响应。如果后端渲染过程阻塞（例如传统同步 SSR），将导致性能下降。

以 React 为例，旧版采用同步渲染，直到全部生成完才发送，而新版 React 支持 流式服务器端渲染（Streaming SSR），可以边渲染边传输，提升响应速度。

Deno 和 Node.js 等运行时原生支持流式 HTML 响应，而部分后端语言可能不支持。对于不需要个性化的页面，构建时生成的静态 HTML 也能立即开始传输内容。

建议检查你所用的框架和运行时是否支持流式传输，并视情况升级或调整，以提升渲染性能。

### 🧠 使用 Service Worker 优化 TTFB

Service Worker 作为浏览器与服务器之间的代理，对文档和资源的 TTFB 有重要影响，效果取决于其缓存策略是否合理。

使用 `stale-while-revalidate` 策略 时，资源会优先从缓存中返回（快速响应），同时在后台异步更新缓存。这对不常变更的文档或资源非常有效，能让页面几乎瞬间加载。

但对于动态内容（如用户登录状态变化），这种策略可能不合适，因为你通常需要从网络获取最新版本。

对于图片、字体等非关键资源，使用 `stale-while-revalidate` 策略可以显著降低 TTFB，同时不影响用户体验。

客户端渲染的 SPA 则推荐采用 App Shell 模型，让页面框架从缓存中即时加载，动态内容在稍后填充，从而加快首屏响应速度。

![20250725144654](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250725144654.png)

### 🚀 使用 `103 Early Hints` 提前加载关键资源

即使后端优化得很好，服务器仍可能在响应前执行大量数据库或计算操作，导致导航延迟。这会影响关键资源（如 CSS、JS）的加载速度。

为缓解这个问题，服务器可以在正式响应前发送 `103 Early Hints` 状态码，提前告诉浏览器哪些关键资源可以先下载，从而提升首屏渲染速度并缩短加载时间。

这方法适合后端处理耗时较长的页面（如 SSR 页面），但是对于静态网站等无需等待后端的场景，效果不明显。

`103 Early Hints` 可能掩盖真实的 TTFB，使问题难以察觉，推荐配合 `PerformanceNavigationTiming` API 或 `Server-Timing` 头部来监控实际服务器耗时

## 总结

TTFB（首字节时间） 是衡量用户从发起请求到接收到第一个响应字节所经历的延迟，是网站性能优化的关键起点。它直接影响后续如 FCP、LCP 等指标，延迟越大，用户看到页面内容的时间就越晚。

> 由于后端技术栈组合繁多，无法用一套方法解决所有 TTFB 问题。更有效的策略是：先通过真实用户数据发现瓶颈，再借助实验室工具深入分析根因，并结合具体情况逐步优化。虽然文中提到的每项优化未必都适用，但总有几项适合你的场景。

最重要的一点是：持续关注现场 TTFB 表现，灵活应用优化策略，才能确保为用户提供稳定、快速的访问体验。
