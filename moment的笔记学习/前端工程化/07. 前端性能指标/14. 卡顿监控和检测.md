卡顿问题是前端开发中最具挑战性的难题之一，尤其是在卡顿发生时，页面常常陷入无响应状态，甚至无法打开开发者工具进行调试。

对于能够在本地复现的情况，还可以借助控制台打断点或录制 Performance，分析具体的性能瓶颈。但一旦无法在本地复现，问题的定位与排查将变得异常困难。

## 卡顿检测

在前端性能监控中，主动检测卡顿的出现是定位和优化性能问题的重要手段。

所谓“卡顿”，通常是指 JavaScript 执行过程中出现了较长的阻塞操作，**导致浏览器无法及时响应用户交互。针对这一问题，我们可以通过多种方案监测页面响应延迟，从而识别出潜在的性能瓶颈**。

### Worker 心跳检测方案

由于浏览器中的 JavaScript 采用单线程模型，卡顿往往是由于主线程长时间执行复杂逻辑（如大规模数据遍历或死循环）所导致。

基于这个特点，我们可以通过 Web Worker 与主线程进行“心跳”通信来检测卡顿。具体做法是：在页面加载时启动一个 Worker，主线程以固定频率（如每秒）向 Worker 发送心跳消息。Worker 监听心跳消息的间隔，如果某次心跳延迟或丢失，即可判断主线程可能发生了卡顿。

需要注意的是，线程间通信本身存在一定的开销，同时 JavaScript 的计时器精度有限，因此在设定阈值时需留有一定冗余。

虽然该方案具备一定可行性，但实际应用中，**Web Worker 更常用于检测页面崩溃**。**由于通信延迟和事件排队的不可控性，其检测卡顿的准确性**不如基于 `window.requestAnimationFrame` 的方法。

### requestAnimationFrame 检测方案

在实际项目中，最常见也最有效的卡顿检测方式是基于 `window.requestAnimationFrame`（简称 rAF）。该方法会在浏览器下一次重绘之前调用回调函数，常用于执行高频率的动画更新。

相比 `setTimeout` 或 `setInterval`，rAF 能更精准地反映浏览器的实际渲染节奏。以常见的 60Hz 屏幕为例，rAF 理论上每秒会执行约 60 次，即每帧约为 16.7ms。因此，监测 rAF 调用之间的时间间隔，就可以较为准确地判断是否发生了卡顿。

**常见的判断标准包括：**

- 若连续出现多帧帧率低于 20 FPS，即可认为页面存在卡顿；
  > 20FPS 是人眼明显能感觉到不流畅、掉帧的分界线；
- 若两次 rAF 回调之间的时间间隔超过一定阈值（如 1000ms），则可视为一次严重卡顿。

不过需要注意，**rAF 的回调本身频率极高，因此在回调函数中应避免执行复杂逻辑，以免对性能造成额外影响**。

### Long Tasks API 方案

在前端性能优化中，一个任务若阻塞主线程 50 毫秒及以上，就会导致一系列问题：

- 可交互时间（TTI）延迟

- 用户交互行为（点击、滚动等）明显延迟

- 事件回调延迟

- 动画与滚动的卡顿或不流畅

为此，**W3C 推出了 Long Tasks API。它将“长任务”定义为：主线程连续繁忙 50 毫秒及以上的执行区间**。常见触发场景包括：

- 长耗时的事件回调

- 高代价的回流与重绘

- 浏览器在相邻事件循环之间执行超过 50 毫秒的工作

使用 PerformanceObserver 我们可以轻松捕获这些长任务：

```js
const observer = new PerformanceObserver((list) => {
  const entries = list.getEntries();
  entries.forEach((entry) => {
    // 分析和上报关键卡顿信息
  });
});

// 注册长任务观察
observer.observe({ entryTypes: ["longtask"] });
```

相较于 `requestAnimationFrame`，Long Tasks API 不会频繁触发回调，且其在性能时间线（Performance Timeline）中的优先级较低，会尽量在空闲时执行，避免干扰页面的其他任务。
不过，该 API 仍处于实验性阶段，浏览器兼容性有限，尤其是在老旧设备或浏览器中，因此仍需配合兜底方案。

### PerformanceObserver 卡顿检测

**卡顿的本质是用户操作后网页无法及时响应**。基于这个原理，可以利用 `PerformanceObserver` 监听用户交互事件，并检测其中的延迟：

```js
new PerformanceObserver((list) => {
  list.getEntries().forEach((entry) => {
    const duration = entry.duration;
    const delay = entry.processingStart - entry.startTime;
    const eventHandlerTime = entry.processingEnd - entry.processingStart;

    console.log(`Total duration: ${duration}`);
    console.log(`Event delay: ${delay}`);
    console.log(`Event handler duration: ${eventHandlerTime}`);
  });
}).observe({ type: "event" });
```

这种方式的优势是无需像 `requestAnimationFrame` 那样高频轮询，且 `PerformanceObserver` 任务是低优先级的，不会明显影响页面性能，并且能够回溯过去的事件数据。

如下代码所示：

```js
<!DOCTYPE html>
<html lang="zh">
  <head>
    <meta charset="UTF-8" />
    <title>PerformanceObserver 卡顿检测 Demo</title>
    <style>
      body {
        font-family: sans-serif;
        padding: 40px;
      }
      button {
        padding: 10px 20px;
        font-size: 18px;
        margin-right: 10px;
        cursor: pointer;
      }
      .log {
        margin-top: 30px;
        background-color: #f9f9f9;
        padding: 15px;
        border-left: 4px solid #333;
        white-space: pre-wrap;
        font-family: monospace;
      }
    </style>
  </head>
  <body>
    <h2>🎯 PerformanceObserver 卡顿检测 Demo</h2>
    <p>点击以下按钮，分别模拟正常响应和卡顿响应，观察事件延迟与处理耗时：</p>

    <button id="normalBtn">✅ 正常点击</button>
    <button id="slowBtn">🐢 模拟卡顿</button>

    <div class="log" id="log"></div>

    <script>
      const logEl = document.getElementById("log");
      function log(text) {
        console.log(text);
        logEl.textContent += text + "\n";
      }

      // 注册 PerformanceObserver，监听用户交互事件
      const observer = new PerformanceObserver((list) => {
        list.getEntries().forEach((entry) => {
          const delay = entry.processingStart - entry.startTime;
          const handlerTime = entry.processingEnd - entry.processingStart;
          const duration = entry.duration;

          log(`🎯 [${entry.name}] Total Duration: ${duration.toFixed(2)} ms`);
          log(`⏱️ Event Delay: ${delay.toFixed(2)} ms`);
          log(`🧠 Handler Time: ${handlerTime.toFixed(2)} ms`);

          if (delay > 100 || handlerTime > 200) {
            log(`⚠️ 检测到卡顿：事件延迟或处理耗时过高`);
          }
        });
      });

      observer.observe({ type: "event", buffered: true });

      // 正常点击：快速响应
      document.getElementById("normalBtn").addEventListener("click", () => {
        log("✅ 正常按钮被点击，立即响应！");
      });

      // 模拟卡顿：执行复杂计算任务（例如：大规模斐波那契递归）
      function heavyCalculation(n) {
        if (n <= 1) return 1;
        return heavyCalculation(n - 1) + heavyCalculation(n - 2);
      }

      document.getElementById("slowBtn").addEventListener("click", () => {
        log("🐢 模拟卡顿中：执行复杂计算...");
        heavyCalculation(40); // 注意：数值大于 35 会明显阻塞页面
        log("✅ 模拟卡顿任务完成");
      });
    </script>
  </body>
</html>
```

`PerformanceObserver` **监听的是用户交互事件的性能指标，只有当事件的响应延迟（delay）或处理耗时（handler time）较高时才会被记录**。一般来说，延迟超过 50ms 或 处理时间超过 100-200ms 的事件就可能被认为是卡顿并触发回调。在 Demo 中，复杂计算如 `Fibonacci(40)` 会明显占用主线程，必然会触发检测。这个机制可用于识别页面中影响用户体验的关键慢操作。

但需要注意的是，这种方式只能发现卡顿，若要进一步定位原因，仍需结合埋点、心跳检测等策略，才能形成有效的性能监控方案。

## 总结

卡顿检测是前端性能监控中的关键环节，主要目的是识别主线程被阻塞、页面响应迟缓的时刻。常用方案包括 `requestAnimationFrame` 检测渲染帧率、`Long Tasks API` 捕捉长时间阻塞任务、以及 `PerformanceObserver` 监听用户事件的响应延迟与处理耗时。

通过这些方案，可以较准确地发现页面中存在的性能瓶颈。尤其是结合复杂计算模拟测试，能够有效验证检测机制的准确性。

但检测只是第一步，若要深入定位卡顿成因，还需配合埋点、心跳等上下文信息进行分析与上报。
