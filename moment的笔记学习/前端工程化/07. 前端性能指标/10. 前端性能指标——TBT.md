## 什么是 TBT

TBT（总阻塞时间）是一项关键的 Web 性能指标，用于衡量页面加载过程中主线程因长任务阻塞而无法响应用户操作的总时长，它直接反映了用户在加载期可能遇到的“卡顿”或“无响应”体验。

**TBT 衡量的是从 FCP 到 TTI 之间，主线程上所有超过 50ms 的任务所造成的阻塞时间总和**。比如某个任务执行了 80ms，其中超出 50ms 的部分（即 30ms）就计入 TBT，所有此类任务的超时部分累加，便构成了页面的总阻塞时间。

![20250726135557](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250726135557.png)

TBT 直接反映了页面加载过程中用户交互的流畅度，TBT 越高，说明主线程越繁忙，用户在点击或输入时可能遇到延迟或无响应的问题。同时，它也是评估 JavaScript 执行效率和主线程调度合理性的重要参考指标。

**最佳的总阻塞时间（TBT）应控制在 300 毫秒以下，以确保良好的用户交互体验。如果 TBT 介于 300ms 到 600ms 之间，则表示还有优化空间，需进一步改善性能。**

当 TBT 超过 600ms，说明页面加载期间主线程严重阻塞，可能导致交互迟钝，建议尽快进行优化处理。

## 如何测量总阻塞时间（TBT）

测量 TBT 的关键在于识别页面加载过程中主线程上所有超过 50ms 的长任务，这些任务的阻塞时间总和即为总阻塞时间。

目前主要有两种测量方式：实验室工具（Lab Tools） 和 现场工具（Field Tools），它们提供的结果大致相似，但适用场景和数据来源略有不同：

### 🧪 实验室工具（Lab Tools）

用于模拟标准环境下的页面加载过程，适合开发阶段调试使用。
常见工具包括：

- [WebPageTest](https://www.webpagetest.org/)

- [Chrome DevTools](https://developer.chrome.com/docs/devtools/)

- [Lighthouse](https://developer.chrome.com/docs/lighthouse/)

### 现场工具（Field Tools）

基于真实用户数据，反映页面在实际访问中的 TBT 表现。常见工具包括：

- [PageSpeed Insights](https://pagespeed.web.dev/)

- [Chrome 用户体验报告（CrUX）](https://developer.chrome.com/docs/crux/)

- [Google Search Console - 核心网络指标报告](https://search.google.com/search-console/core-web-vitals)

在本文中，我们将使用 [Chrome DevTools](https://developer.chrome.com/docs/devtools/) 来测量和分析页面的 TBT，直观查看主线程上耗时任务的分布与影响。

## 如何优化

### 最小化浏览器主线程的负载

浏览器主线程负责执行页面的解析、脚本执行、样式计算、布局和渲染等关键任务。任何任务阻塞主线程，都会直接影响页面的响应性和性能表现。

页面渲染流程通常包括：脚本评估 → 样式和布局 → 渲染 → 解析 HTML/CSS → 脚本解析与编译 → 垃圾回收。通过性能面板，你可以清楚地识别哪些流程占用了异常的主线程时间，并针对性地优化。

常见优化建议如下：

- 脚本评估
  - 减少抖动处理（debounce/throttle）
  - 利用 Service Worker 脱离主线程
  - 精简并延迟第三方 JavaScript

- 样式与布局
  - 避免复杂嵌套与大范围样式重计算
  - 控制样式作用域，减少强制回流

- 渲染阶段
  - 使用合成属性（如 `transform`、`opacity`）避免主线程绘制
  - 控制绘制区域和图层数量，降低绘制复杂度

- HTML / CSS 解析
  - 提取关键 CSS，优先加载首屏样式
  - 最小化 CSS 体积，延迟非关键样式加载

- 脚本解析与编译
  - 使用代码分割（Code Splitting）降低首次加载压力
  - 移除无效/未使用代码

- 垃圾回收
  - 使用 `performance.measureMemory()` 监控整体内存使用，防止内存泄漏

通过以上方法，可以有效减少主线程负担，优化页面在加载和交互过程中的响应速度与稳定性。

### 减少第三方代码的影响

第三方代码通常用于添加插件、分析工具、广告脚本或社交媒体集成功能，虽然它们提升了网站功能性，但如果未经过优化，往往会显著阻塞浏览器主线程，导致性能下降。

常见问题包括：

- 未优化的 iframe 阻塞 `window.onload` 事件，延迟页面完全加载；

- 长任务阻塞主线程，降低首次交互性能（TTI）和总阻塞时间（TBT）表现。

因此，合理管理和精简第三方代码至关重要：

- 分析所有引入的第三方脚本，识别性能瓶颈；

- 移除不必要的依赖项，尤其是加载后无明显价值的脚本；

- 延迟或异步加载非关键资源，避免其阻塞渲染路径；

- 优先选择体积小、加载快、性能优化良好的第三方库。

通过这些优化措施，可有效降低第三方代码对主线程的占用，提升整体页面性能和用户体验。

### 减少 JavaScript 执行时间，提高交互性能

JavaScript 的编译、解析与执行是造成总阻塞时间（TBT）上升的主要原因。执行时间越长，主线程越容易被占用，从而导致页面响应变慢、交互迟钝，甚至出现高内存占用和网络资源消耗过大的问题，最终严重影响用户体验。

为了有效减少 JavaScript 执行时间，你可以采用以下优化策略：

- 延迟加载不必要的 JS 脚本
- 实现代码分割，只加载当前页面所需模块
- 压缩并缩小 JavaScript 文件体积
- 使用 [PRPL](https://web.dev/articles/apply-instant-loading-with-prpl?hl=zh-cn) 模式优化加载路径，包括：
  - 预加载关键脚本
  - 首屏优先渲染
  - 预缓存核心资源
  - 延迟加载非关键功能模块

此外，渲染模式也会对 TBT 表现产生显著影响。服务器端渲染（SSR） 虽能带来较早的 FCP，但在 JavaScript 加载完成前页面并不可交互，可能误导用户；而 客户端渲染（CSR） 则将大部分逻辑放在浏览器侧执行，虽提升了灵活性，但也对 JS 执行效率提出了更高要求。

因此，优化 JavaScript 的加载和执行路径，是提升页面可用性和交互性能的关键手段。

## 总结

TBT（总阻塞时间）用于衡量页面在加载过程中，主线程被长任务阻塞而无法响应用户交互的时间总和，是评估页面“卡顿感”的核心指标之一。

它专注于 FCP（首次内容绘制）到 TTI（可交互时间）之间的任务，计算所有超过 50ms 的脚本任务所造成的阻塞总时长。TBT 过高通常意味着 JavaScript 执行过重、主线程负担过重，从而影响用户点击、滚动等操作的即时响应。

理想的 TBT 应控制在 300ms 以下，开发者可以通过代码拆分、异步加载、减少第三方脚本等方式有效降低它。优化 TBT 不仅提升用户体验，也显著改善页面在核心指标中的整体性能评分。
