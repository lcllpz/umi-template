**FPS（每秒帧数**）表示浏览器每秒绘制画面的次数，60FPS 意味着每秒渲染 60 帧，也就是每帧耗时约 16.67 毫秒。只有当每一帧都能在这个时间内完成渲染，动画才会保持流畅、不卡顿。稳定的 60FPS 表现为每一帧间隔时间均匀，用户看到的画面移动顺滑，没有跳帧或延迟。FPS 不稳定或过低通常说明渲染负担过重，可能导致视觉上的卡顿和体验下降。

## setTimeout

使用 `setTimeout` 做动画是通过设定一个定时器，让某个函数在指定的时间间隔后执行，比如每 16ms 调用一次，从而模拟 60FPS 的效果。然而，`setTimeout` 并不会严格按照指定时间执行，它受浏览器线程调度、页面负载等影响，可能提前或延迟触发，导致动画帧与帧之间间隔不一致。

由于`它与浏览器的屏幕刷新率不同步`，这种方式很容易出现掉帧、卡顿甚至跳帧等问题，视觉上会感到动画不平滑。因此，`setTimeout` 并不是为高频动画设计的，通常不推荐用于需要流畅性的动画场景。

如下代码所示：

```js
<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>setTimeout vs requestAnimationFrame</title>
    <style>
      #box {
        width: 100px;
        height: 100px;
        background-color: red;
        position: absolute;
        top: 50px;
      }
    </style>
  </head>
  <body>
    <div id="box"></div>

    <script>
      const box = document.getElementById("box");
      let position = 0;
      let counter = 0;

      function simulateHeavyTask() {
        // 进行一些计算密集型的任务，增加CPU负担
        for (let i = 0; i < 1e6; i++) {
          counter += Math.random();
        }
      }

      function animate() {
        simulateHeavyTask(); // 每一帧都进行计算密集型任务

        position += 2; // 每次更新，增加2像素
        box.style.left = position + "px"; // 更新方块的位置

        // 使用 setTimeout 来模拟动画的逐帧效果
        if (position < window.innerWidth - 100) {
          setTimeout(animate, 1000 / 60); // 每 16.67ms 更新一次，相当于60fps
        }
      }

      // 启动动画
      setTimeout(animate, 1000 / 60);
    </script>
  </body>
</html>
```

从性能面板可以看出，黄色尖峰图代表帧时间分布，虽然中后期帧数趋于均匀，但仍存在锯齿波动，说明浏览器未能稳定保持 60FPS，`setTimeout` 存在时间偏差，导致部分帧拉长、掉帧。Frames 时间线中最左侧一帧耗时高达 492.9ms，属于严重卡顿，后续帧虽相对平稳，但普遍在 26\~40ms，远高于理想的 16.67ms，帧率仅约 25FPS，动画仍有“微卡感”。同时，Layout Shifts 中紫色条频繁出现，说明动画频繁修改了如 `top`、`left` 等属性，触发布局重排，增加了渲染负担，进一步影响流畅度。

- Idle frame：「这一帧主要是浏览器在等下一拍 / 合成在交帧，主线程相对空着」，DevTools 就把它标成 Idle
  > 用 setTimeout 驱动动画 时，回调 不会和屏幕刷新严格对齐，所以你会看到 有的帧 ~24ms，有的 ~30ms，并且会出现 「上一段任务刚跑完 → 中间空一截 → 下一拍 Timer 才来」 的形态。
  > 红框里那段 Idle frame，多半就是 夹在两次 setTimeout 触发之间的那一小段「主线程相对安静」的时间，画面上可能几乎没变，但时间仍在走，所以仍算一帧并标了时长。

## requestAnimationFrame

使用 `setTimeout` 做动画存在时间精度差、与屏幕刷新不同步等问题，常导致帧率不稳定和视觉卡顿。它无法保证每帧在合适的时机执行，尤其在页面负载较高时更易掉帧。

为了解决这些问题，浏览器提供了专门用于高性能动画的 API —— `requestAnimationFrame`。

我们现在将上面的代码修改成下面这样：

```js
<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>requestAnimationFrame vs setTimeout</title>
    <style>
      #box {
        width: 100px;
        height: 100px;
        background-color: red;
        position: absolute;
        top: 50px;
      }
    </style>
  </head>
  <body>
    <div id="box"></div>

    <script>
      const box = document.getElementById("box");
      let position = 0;
      let counter = 0;

      function simulateHeavyTask() {
        // 进行一些计算密集型的任务，增加CPU负担
        for (let i = 0; i < 1e6; i++) {
          counter += Math.random();
        }
      }

      function animate() {
        simulateHeavyTask(); // 每一帧都进行计算密集型任务

        position += 2; // 每次更新，增加2像素
        box.style.left = position + "px"; // 更新方块的位置

        // 如果方块没有移动到屏幕右边，继续调用 requestAnimationFrame 进行下一帧更新
        if (position < window.innerWidth - 100) {
          requestAnimationFrame(animate);
        }
      }

      // 启动动画
      requestAnimationFrame(animate);
    </script>
  </body>
</html>
```

从性能面板来看，黄色尖峰图波动趋于平稳，帧间隔均匀，说明动画帧率已基本稳定接近 60FPS。Frames 时间线连续紧凑，无明显丢帧或大间隙，说明每帧渲染及时、动画流畅。主线程任务密度合理，JavaScript 和样式计算耗时分布均匀，无明显阻塞帧。GPU 与线程池均正常工作，表示动画可能已启用 `transform` 等高性能属性。整体表现说明当前动画性能已大幅优化，已达推荐实践水平。
![alt text](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images202507231717112.png)

- Partially-presented frame（部分呈现帧） 表示：这一帧已经显示到屏幕上了，但这次刷新并没有把你页面里「该一起上去」的改动都完整带上——有一部分内容 没赶上这一帧的合成/栅格化截止时间，只能 下一帧（或更晚）再补，所以叫「部分呈现」。
- Animation frame fired → animate → simulateHeavyTask
  只要某一拍里 simulateHeavyTask 把主线程占得比较满（或导致样式/布局/绘制相关的工作来不及在这一帧的呈现窗口内全部完成），就可能出现：合成层里 已经有的内容先被提交显示；还没准备好的那部分更新 只能跟到后面一帧。于是 Frames 里就会出现 Partially-presented frame。
- 正常就是Frames ：浏览器的一次「帧」（一次往屏幕上交画面的周期）。格子上写的 6.0 ms / 6.1 ms：这一帧在时间轴上大约占多久。

## 总结

在进行基于时间的动画时，很多人最初会选择使用 `setTimeout`，但它并不是为高精度动画设计的。首先，`setTimeout` 的定时并不完全精确，它会受到多个因素影响。比如：浏览器如果正忙于渲染、解析事件或执行脚本、微任务或者其它任务堆积，`setTimeout` 的回调函数就可能被延迟执行；其次，**浏览器和操作系统对定时器的调用通常有最小限制，一般为 4ms 或 10ms，即使你设置为 0 或 16ms，也可能被系统调节；**更关键的是，在连续的动画帧中，时间上的微小偏差会逐步累积，造成动画时快时慢、速度不一致，影响观感体验。

为了解决这些问题，现代浏览器提供了更高效的动画方式 —— `requestAnimationFrame`。这个 API 会在每一帧浏览器准备渲染之前自动调用你的回调函数，与显示器的刷新频率同步（通常为 60FPS），因此动画可以更自然、更流畅。此外，它还能自动在页面不可见时暂停执行，节省资源。结合每帧的 `timestamp`（当前时间），我们可以精准控制动画速度，避免累积误差带来的动画偏差。
