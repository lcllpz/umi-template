LCP 是 Core Web Vitals 中用于衡量网页主要内容何时完成渲染的关键指标，能准确反映用户真正看到页面核心内容的时间点。

相比之下，传统指标如 `load` 或 `DOMContentLoaded` 只能表示技术层面的加载完成，无法体现用户实际的视觉体验。即使是 `FCP` 也只**是代表首个内容出现**，若只是加载动画或骨架屏，对用户来说几乎没有实际价值。

## 什么是 LCP

LCP 是衡量用户感知网页加载速度的关键性能指标之一，用于标记**视口中最大内容元素从导航开始到完全渲染所需的时间**。这个时间点通常代表用户认为“页面有用了”。

根据 [Largest Contentful Paint API](https://w3c.github.io/largest-contentful-paint/) 的定义，浏览器会选取以下类型中面积最大的元素作为 LCP 候选：

- `<img>` 元素（包括静态图与非 GIF 动态图）

- SVG 图像中的 `<image>` 元素（部分支持）

- `<video>` 元素的海报图（封面帧）

- 使用 `url()` 加载的背景图像（不是 CSS 渐变）

- 块级文本元素（如 `<h1>`、`<p>`），通常用于页面主标题或正文段落

浏览器会自动排除一些对用户无意义或不可见的元素，如：

- 设置为 `opacity: 0`、`visibility: hidden` 或 `display: none` 的元素

- 被遮挡的元素，或完全在视口外的部分

- 非内容性图像（如透明图、1x1 像素图）

- 图像占位符或懒加载尚未完成的图像

值得注意的是，**虽然视频或动画加载后的第一帧可能已经显示，但这部分目前不会被计入 LCP 指标**。我们可以在开发工具或 API 中看到这些信息，但它们不会包含在 LCP 的性能统计数据（如 CrUX）中。这是因为当前 **LCP 的实现主要聚焦于静态内容的视觉完成度，而非动态图像的首帧展示**。

## LCP 得分多少算好？

为了提供良好的用户体验，网站应尽量将 `Largest Contentful Paint` 控制在 2.5 秒或更短的时间内。为确保大多数用户都能达到此目标值，一个合适的衡量阈值是网页加载时间的第 75 个百分位数，并按移动设备和桌面设备进行细分。

![20250724110413](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250724110413.png)

这个阈值设定在保障全球用户获得良好体验的同时，充分考虑了网络质量与设备性能的差异。

根据 Google 的测试数据：

- 只有约 10% 的网站能够达到“良好”体验的标准；
- 使用第 75 百分位数作为衡量标准，更能全面反映大多数用户的实际体验是否达标。

要让用户感知页面快速加载，LCP ≤ 2.5 秒（75% 百分位） 是行业公认的“理想标准”。若介于 2.5–4 秒，需进行优化；若超出 4 秒，则严重影响体验，应当优先改进。

## 为什么 LCP 这么重要

相比传统的指标（如 DOMContentLoaded 或 load），而 LCP 通常对应用户判断网页是否“有价值” 的时间点，比如大标题、主图、关键商品信息等，是“网页已经开始可用了”的标志。

### 用户体验

### Google 将 LCP 作为核心 Web Vitals 之一，并纳入排名算法

自 2021 年起，Google 正式将 LCP（最大内容绘制时间） 纳入搜索排名算法中的 “页面体验（Page Experience）” 核心评估标准之一。

这意味着：

> 优化 LCP 不再只是提升加载速度或用户满意度，更直接影响到我们的网站在搜索结果中的排名表现。

如果页面加载缓慢，即使内容优质、设计美观，也可能因体验不佳而排名靠后。相反，一个加载迅速、体验顺畅的网页更容易获得搜索引擎的青睐，在自然搜索中脱颖而出。

### 直接关联用户行为

当网页的 LCP 延迟每增加 1 秒，用户跳出率就会明显上升。也就是说，加载越慢，用户越容易中途离开，甚至根本不会等到主要内容加载出来。

相反，如果页面加载得更快，用户更有可能留下来继续浏览、深入查看更多内容，最终完成购买或其他转化操作。这不仅提升了用户体验，也直接推动了业务目标的实现。

因此，LCP 不只是一个前端性能指标，它本质上是一项直接影响用户留存和商业转化的关键因素。优化 LCP，就是在优化用户满意度与业务增长的双赢路径。

Vodafone 是全球最大的无线服务提供商之一，拥有超过 `90,000` 名员工，业务遍及 `22` 个国家。根据 Google 发布的一项案例研究，该公司通过提升 LCP（最大内容绘制时间）`31%`，实现了 销售额增长 `5%`，原因是更多网站访客转化为实际购买者。以 Vodafone 的规模来看，这一增长相当于数千万美元的额外收入。

他们进行了一次 `A/B` 测试，分别使用两个着陆页（如下图所示），每个页面都接收了 34,000 名访客，流量来源包括展示广告、社交媒体和自然搜索等多个渠道。

## LCP 细分

大多数网页加载过程中通常会发起多个网络请求，**但在优化 LCP 时，建议优先关注以下两个关键请求：**

1. 初始 HTML 文档
2. LCP 资源（如果适用）

虽然页面上的其他请求也可能影响 LCP，但这两项（尤其是 LCP 资源的请求起始和结束时间）最能揭示页面是否针对 LCP 做出了优化。

要识别 LCP 资源，可先定位对应的 LCP 元素，然后在网络瀑布图中查找其加载请求（如图片地址），分析其加载顺序和耗时情况（如果适用）。

例如，下图展示了一个典型网页的网络瀑布图，图中已高亮显示关键资源，其中 LCP 元素需通过图片请求加载完成后才能呈现。

![20250724142843](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250724142843.png)

对于经过良好优化的网页，理想情况是 LCP 资源尽早开始加载，并在加载完成后尽快完成渲染。为了更直观地评估网页是否达到了这一目标，LCP 时间通常可以拆分为以下四个阶段：

1. 首字节时间（TTFB）：用户发起加载请求后，浏览器接收到 HTML 文档第一个字节的时间。

2. 资源加载延迟：从收到首字节到浏览器开始加载 LCP 资源之间的间隔。若 LCP 元素无需加载外部资源（如系统字体的文本），此值为 0。

3. 资源加载时长：LCP 资源本身的加载时间。如果无需加载资源，则为 0。

4. 元素渲染延迟：LCP 资源加载完成后，到元素真正完成渲染之间的时间。

这四部分组成了完整的 LCP 时间，彼此之间无重叠或间隔，总和即为最终的 LCP 值。

![20250724143029](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250724143029.png)

每个网页的 LCP 时间都可以拆分为四个连续的子部分，它们之间没有重叠或空隙，总和即为完整的 LCP 值。

在优化 LCP 时，分别分析并优化这四个阶段是非常有效的做法。但需要注意的是，仅优化其中一个阶段并不一定改善整体 LCP，有时只是将耗时从一个部分转移到了另一个部分。

例如，在前面的网络瀑布图中，如果我们通过更高压缩率或使用更高效的格式（如 AVIF 或 WebP）减少图片体积，确实可以缩短资源加载时长，但如果浏览器在资源加载完成后仍花较长时间才开始渲染，LCP 总时长并不会缩短，延迟只是被转移到了“元素渲染延迟”阶段。

![20250724143157](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250724143157.png)

出现这种情况的原因是，在此网页上，LCP 元素会一直处于隐藏状态，直到 JavaScript 代码加载完毕，然后所有内容都会同时显示。

此示例有助于说明，我们需要优化所有这些子部分，才能取得最佳 LCP 效果。

为了有效优化 LCP 的各个组成部分，了解理想情况下它们在优秀网页中的时间分布将非常有帮助。

在四个子部分中，部分名称中带有“延迟”字样，表示这些时间应尽可能接近零。而其余两部分则与网络请求有关，天然存在一定耗时。

| LCP 子部分             | LCP 占比（%） |
| ---------------------- | ------------- |
| 加载第一个字节所需时间 | \~40%         |
| 资源加载延迟           | <10%          |
| 资源加载时长           | \~40%         |
| 元素渲染延迟           | <10%          |
| 总计                   | 100%          |

请注意，这些时间占比仅为通用建议，并非严格标准。如果页面的 LCP 总时间控制在 2.5 秒以内，则具体占比并不是重点。但如果某一“延迟”阶段的耗时偏高，就可能难以达成 2.5 秒 LCP 优化目标。

## 如何优化各个部分

在了解了优化良好的网页中各个 LCP 子部分的时间分布后，接下来我们可以开始着手优化自己的页面，我们将按影响程度从高到低依次介绍每个阶段的优化建议与最佳实践。

### 1. 消除资源加载延迟

本步骤的目标是尽可能让 LCP 资源尽早开始加载；虽然理论上它可以在 TTFB 之后立即发起请求，但实际情况中往往存在一定延迟，因此理想状态是它能与页面的第一个资源同时开始加载，换句话说，若其加载时间明显滞后于首个资源，则仍有优化空间。

![20250724145039](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250724145039.png)

影响 LCP 资源加载速度的两个关键因素是：资源被浏览器发现的时机和资源的加载优先级。

为了确保 LCP 资源尽早加载，应尽可能让浏览器在解析初始 HTML 响应时就能发现该资源。例如，以下做法是理想的：

- LCP 元素是 `<img>`，并且其 `src` 或 `srcset` 属性直接出现在 HTML 中。

- 背景图像通过 `<link rel="preload">` 或 Link 响应头进行预加载。

- LCP 使用 Web 字体，且字体在 HTML 中被显式预加载。

相反，以下情况会导致浏览器延迟发现资源，进而影响加载时机：

- `<img>` 元素由 JavaScript 动态插入。

- 图片通过懒加载库设置为 `data-src` 或 `data-srcset`。

- 背景图片未预加载，仅定义在外部 CSS 中。

在这些情况下，浏览器必须等待脚本或样式加载完成才能识别资源，显著增加延迟。

因此，最佳做法是确保 LCP 资源可在 HTML 中被直接发现，若必须通过外部文件引用，应使用 `<link rel="preload">` 或响应头方式提升其加载优先级。

例如：

```html
<!-- Load the stylesheet that will reference the LCP image. -->
<link rel="stylesheet" href="/path/to/styles.css" />

<!-- Preload the LCP image with a high fetchpriority so it starts loading with the stylesheet. -->
<link
  rel="preload"
  fetchpriority="high"
  as="image"
  href="/path/to/hero-image.webp"
  type="image/webp"
/>
```

即使 LCP 资源能被 HTML 正确引用，如果浏览器未能识别其重要性，也可能不会优先加载。这通常发生在浏览器根据启发式判断其他资源更重要，或开发者错误设置了优先级。

例如，在 `<img>` 元素上添加 `loading="lazy"` 会延迟其加载，直到浏览器确认图片位于视口中，这会导致 LCP 图片加载延迟，应避免延迟加载 LCP 图片，因为这始终会对 LCP 产生负面影响。

此外，即使未启用延迟加载，浏览器默认也不会将图片视为高优先级资源（因为图片不属于阻塞渲染的关键资源）。为了提升重要图片的加载优先级，可使用 [`fetchpriority`](https://developer.mozilla.org/en-US/docs/Web/API/HTMLImageElement/fetchPriority) 属性明确提示浏览器其重要性：

```html
<img fetchpriority="high" src="/path/to/hero-image.webp" />
```

如果我们确定该图片可能是页面的 LCP 元素，推荐设置 `fetchpriority="high"`。但请注意，不要为多张图片同时设置高优先级，否则会稀释带宽分配，对 LCP 无益。

同样地，对于页面初始不可见的图片（如轮播图后几张），可主动降低其优先级，释放带宽：

```html
<img fetchpriority="low" src="/path/to/carousel-slide-3.webp" />
```

调整优先级时应谨慎，建议在 DevTools 中检查实际资源加载顺序，并通过实验室或真实用户工具验证优化效果。

优化 LCP 资源的优先级和发现时间后，我们的网络广告瀑布流应如下所示（LCP 资源与第一个资源同时开始加载）：

![20250724145529](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250724145529.png)

### 2. 消除元素渲染延迟

造成 LCP 元素延迟渲染的常见原因通常不是资源加载慢，而是渲染被其它因素阻塞，例如：

- `<head>` 中的样式表或同步脚本仍在加载，阻止页面渲染；

- LCP 元素虽然资源已加载，但尚未插入 DOM（通常在等待 JavaScript 执行）；

- 元素被 A/B 测试等逻辑暂时隐藏，直到某些条件判定完成；

- 主线程被长任务占用，浏览器无法及时进行渲染。

以下几部分将介绍如何排查和解决这些常见的渲染延迟问题。

#### 减少阻塞渲染的样式表，或将关键样式内联

从 HTML 引入的外部样式表在加载完成前会阻止页面渲染，这是为了避免“无样式内容”闪现。但如果这些样式表体积较大，加载速度明显慢于 LCP 资源，就会造成 LCP 元素“资源已就绪但无法渲染”的现象。

为此，我们可以考虑：

- 优化样式体积，移除未用 CSS；

- 提取关键 CSS 内联到 HTML 中；

- 延迟加载非关键样式，或将其标记为 `media="print"` 后通过 JS 动态切换。

这些做法可以显著减少渲染阻塞时间，确保 LCP 元素在资源加载完成后能立即呈现。

为避免样式阻塞 LCP 元素渲染，可采取以下两种方式之一：

- 将样式表内嵌到 HTML 中，避免额外的网络请求；

- 减小样式表体积，加快其加载速度。

一般来说，只有当样式表较小时才建议内嵌，因为内嵌样式无法被浏览器缓存，不利于后续页面加载。如果样式表较大，其加载时间超过 LCP 资源，就不适合内嵌。

更稳妥的做法是：将关键样式控制在小于 LCP 资源的体积内，以确保样式不会成为 LCP 渲染的瓶颈。

以下是优化样式体积的常用方法：

- 移除未使用的 CSS：可通过 Chrome DevTools 检查哪些样式没有被实际应用。

- 推迟非关键样式：将 CSS 拆分为“关键”与“可延迟”两部分，仅初始加载必要样式，其余使用懒加载。

- 压缩与精简 CSS：移除空格、注释，使用工具压缩以减少传输体积。

例如我们上面提到的，Tiptap 这个编辑器我们首页根本不需要用到的，我们完全可以延迟加载，这样就能减少一部分的时间了。

#### 延迟或内嵌阻塞渲染的 JavaScript

网页中几乎不应在 `<head>` 中添加同步脚本（即没有 `async` 或 `defer` 的脚本），因为它们会阻塞页面渲染，降低性能。

如果某段 JavaScript 确实需要尽早执行，建议将其内嵌到 HTML 中，避免额外的请求延迟。但同样地，只有在脚本体积非常小时才建议这样做，以避免影响缓存效率。

错误的做法：

```html
<head>
  <script src="/path/to/main.js"></script>
</head>
```

正确的做法应该是这样：

```html
<head>
  <script>
    // Inline script contents directly in the HTML.
    // IMPORTANT: only do this for very small scripts.
  </script>
</head>
```

#### 使用服务器端渲染（SSR）

服务器端渲染（SSR） 是指在服务器上运行前端应用逻辑，并返回已渲染好的完整 HTML 响应。

从 LCP 优化角度来看，SSR 有两个显著优势：

1. 图片等资源可直接在 HTML 中被浏览器识别，便于提前加载；

2. 页面内容无需等待 JavaScript 执行即可渲染，提升首屏可见速度。

SSR 的主要缺点是可能会增加服务器处理时间，进而影响 TTFB。但这种延迟通常是可控的，且相比用户侧不可控的设备性能或网络状况，在服务端完成渲染通常是更可取的权衡。

若项目架构支持，也可以选择 静态网站生成（SSG）或预渲染，在构建阶段生成 HTML 页面，进一步提升加载性能，减少服务器负担。

#### 拆分长任务，避免主线程阻塞

即使 JavaScript 没有直接阻塞渲染或控制 LCP 元素，主线程上的长任务依然可能延迟 LCP。

常见问题是：页面加载了体积较大的 JavaScript 文件，浏览器需在主线程中解析和执行，这会占用渲染所需资源。即便 LCP 图片已下载完成，渲染仍可能被这些 JS 执行阻塞。

目前所有主流浏览器都在主线程中完成图片渲染，任何阻塞主线程的操作都有可能延迟 LCP 元素的呈现。

### 3. 缩短资源加载时长

缩短资源加载时间最有效的方法是通过缓存或 CDN 将资源尽可能从本地获取，彻底绕过网络请求。通过设置高效的缓存策略，用户在后续访问中可直接从本地缓存中加载资源，几乎将加载时长降为零。

若 LCP 资源是 Web 字体，除了压缩字体本身，还应使用 `font-display: swap` 避免字体阻塞渲染；否则即使字体加载完毕也可能延迟 LCP 呈现。

此外，若资源体积较小，也可考虑内嵌为数据 URL，但要注意它无法被缓存，且可能因解码耗时导致渲染延迟。除了资源本身优化外，借助 CDN 可将服务器部署在接近用户的位置，进一步减少加载距离与延迟，尤其是图片 CDN，往往还能自动压缩图片，实现传输距离与体积的双重优化。

### 4. 缩短 TTFB（首字节时间）

本步骤的目标是尽可能快速返回初始 HTML。虽然开发者对这一环节的控制力相对较小，但它是整个加载流程的起点，直接影响后续所有性能指标。在服务器返回首字节之前，前端无法执行任何操作，因此任何缩短 TTFB 的优化，都会连带提升 LCP、FCP 等关键指标。

TTFB 较慢的常见原因包括：

- 过多重定向：例如通过广告跳转或短链访问，增加响应链路，建议尽量减少不必要的重定向。

- CDN 回源频繁：边缘节点无法命中缓存，导致每次请求都回源。常见诱因是 URL 中携带了唯一的分析参数，虽然这些参数不影响页面内容，但会让 CDN 误判为不同资源，降低缓存命中率。

优化 TTFB 的关键在于：减少重定向、提升缓存命中率、降低源站响应延迟，为页面加载打好第一步基础。

## 总结

LCP（最大内容绘制）衡量网页主要内容加载完成所需的时间，是影响用户加载体验的重要指标。**优化 LCP 的关键在于四个方面：尽早加载 LCP 资源、资源加载后立即渲染元素、在不影响质量的前提下缩短加载时间、以及尽快返回初始 HTML 文档**。只要围绕这四步展开优化，就能有效提升页面的首屏加载表现，让用户更快看到核心内容，从而改善整体性能得分和体验。
