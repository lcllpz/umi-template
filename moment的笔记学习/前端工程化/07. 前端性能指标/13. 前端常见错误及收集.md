在前端开发中，各类错误无可避免地贯穿于开发、测试与线上运行阶段。了解和分类这些错误，有助于我们更高效地排查问题并构建更稳定的前端系统。

## 一、常见的前端异常类型

1. 语法错误：编译阶段即可捕获的错误，如拼写错误、语法不规范等。

2. JavaScript 运行时错误：运行时触发的异常，如属性或方法不存在、变量未定义、类型错误、浏览器兼容性问题等。

3. 静态资源加载失败：资源如图片、CSS、JS 等加载失败，通常由路径错误、网络异常或 CDN 问题引起。

4. 接口请求异常：包括 Ajax、Fetch、WebSocket 请求失败，原因可能是网络中断、超时、服务器错误或数据异常等。

5. Promise 异常未捕获：异步逻辑中未正确处理 `.catch` 或 `try...catch`，导致错误冒泡或程序中断。

6. 框架运行错误：框架自身或组件运行中的错误，如 React 的渲染异常、Vue 的响应式问题、Angular 生命周期出错等。

## JS 错误

在 JavaScript 中，错误（Error）是程序运行时异常的核心表现形式。为了更好地识别与处理不同类型的问题，JS 提供了一系列内置的错误对象，每种类型代表一种特定的异常场景。下面列举了几种常见的错误类型及其含义与触发示例：

| 类型             | 含义            | 说明                                                                                               |
| ---------------- | --------------- | -------------------------------------------------------------------------------------------------- |
| `Error`          | 错误基类        | 所有错误的基类，使用 `new Error()` 创建，包含 `name`（错误类型）和 `message`（错误信息）两个属性。 |
| `SyntaxError`    | 语法错误        | 代码不符合 JavaScript 语法规则，通常在代码执行前被捕获。                                           |
| `ReferenceError` | 引用错误        | 引用了尚未声明的变量，例如：`let a = undefinedVariable;`                                           |
| `RangeError`     | 范围错误        | 数值超出有效范围，例如：`new Array(-1)` 创建数组时传入了负数长度。                                 |
| `TypeError`      | 类型错误        | 操作数类型不合法，例如：`let foo = 3; foo();` 尝试把数字当作函数调用。                             |
| `URIError`       | URI 处理错误    | `encodeURI` / `decodeURI` 函数使用不当，例如：`decodeURIComponent('%')`。                          |
| `EvalError`      | `eval` 执行错误 | 与 `eval()` 函数相关的错误，现代浏览器中较少出现，通常被归类为 `TypeError`。                       |

### 1. `Error` - 错误基类

`Error` 是所有错误类型的基类。可以直接使用 `new Error(message)` 创建一个通用错误对象。

如下代码所示：

```js
const error = new Error("这是一个通用错误");
console.log(error);
console.log(error.name); // Error
console.log(error.message); // 这是一个通用错误
```

![20250728135033](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250728135033.png)

它的特点主要有这两个方面：

- 通常用于自定义错误

- 不带具体错误类型，仅提供错误信息

### 2. `SyntaxError` - 语法错误

当 JavaScript 代码语法不符合规范时，会在解析阶段抛出错误。

如下代码所示：

```js
eval("var a = )");
```

![20250728135111](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250728135111.png)

`SyntaxError` 通常发生在代码解析阶段，属于语法结构错误，甚至在代码运行前就会抛出。它无法通过 `try...catch` 捕获，除非是在动态执行代码（如 `eval()`）时触发。为避免这类错误，建议使用现代 IDE 或 ESLint 等工具进行静态语法检查。

### 3. `ReferenceError` - 引用错误

当访问一个从未声明过的变量或对象时，就会抛出 `ReferenceError`，这是非常常见的一类运行时错误。

```js
console.log(a); // ReferenceError: a is not defined
```

这类错误通常由于变量拼写错误、作用域遗漏或提前访问变量等原因引起。好在可以通过 `try...catch` 捕获，便于定位问题。

建议开启 `'use strict'` 严格模式，并结合 TypeScript 或 ESLint 等工具，在编译阶段就提前发现潜在引用问题。

### 4. `RangeError` - 范围错误

当某个数值参数超出了函数允许的范围时，会抛出 `RangeError`。常见场景如创建数组时传入了负数长度，或超出了最大递归深度等。

如下代码所示：

```js
const arr = new Array(-1); // RangeError: Invalid array length
```

![20250728135627](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250728135627.png)

这类错误多发生在数组构造、数值运算或递归逻辑中，属于逻辑边界未处理好的典型表现。

应提前对用户输入或变量值做边界校验，尤其在涉及数组长度、分页参数、递归调用等场景中格外注意。

### 5. `TypeError` - 类型错误

当我们对一个值执行了不符合其类型的操作时，就会抛出 `TypeError`。比如把一个数字当成函数调用，或者试图读取 `undefined` 上的属性。

如下代码所示：

```js
const foo = 3;
foo(); // TypeError: foo is not a function
```

![20250728135716](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250728135716.png)

这是前端开发中最常见的错误类型之一，很多时候都是因为类型判断不严谨，或者忘记处理 `null` / `undefined` 等空值。

可以在关键操作前添加类型判断（如 `typeof`、`instanceof`），也可以借助 TypeScript 或 JSDoc 等工具从源头限制类型错误的发生。

### 6. `URIError` - URI 编码错误

`URIError` 通常发生在使用 URI 编码函数（如 `decodeURIComponent` 或 `encodeURI`）时传入了格式非法的字符串，比如缺失了转义字符或语法不完整。

如下代码所示：

```js
decodeURIComponent("%"); // URIError: URI malformed at decodeURIComponent
```

![20250728140017](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250728140017.png)

这种错误比较少见，主要出现在处理 URL 编解码时，特别是当用户输入未经验证就直接传给相关函数时。

在调用这些函数之前，应该先校验字符串是否合法，必要时用 `try...catch` 包裹调用，防止异常中断程序执行。

### 7. `EvalError` - `eval()` 执行错误

`EvalError` 是与 `eval()` 函数相关的一种历史遗留错误类型。在现代 JavaScript 环境中，它已经很少被真正触发，大多数情况下类似错误会被归类为 `SyntaxError` 或 `TypeError`。

如下代码所示：

```js
// 人为抛出 EvalError
throw new EvalError("Eval 错误");
```

这类错误极为罕见，基本不会在实际开发中自然出现，更多是出于学习或测试目的被手动抛出。

最佳方式是避免使用 `eval()`。它不仅可能导致错误，还存在安全和性能隐患，绝大多数场景下都可以用更安全的替代方案实现相同功能。

## 获取资源加载错误

资源加载错误指的是在页面加载过程中，静态资源（如图片、CSS、JS、字体等）无法成功加载，从而触发浏览器的错误事件。这类错误不会抛出 JS 异常，但**可以通过 `error` 事件或全局监听捕捉到**。

常见的资源类型与加载方式主要有以下几个方面：

| 资源类型  | 加载方式                             | 示例                   |
| --------- | ------------------------------------ | ---------------------- |
| 图片      | `<img src="...">`                    | 图片链接失效、路径错误 |
| 样式表    | `<link rel="stylesheet" href="...">` | CDN 不可用、网络超时   |
| 脚本      | `<script src="...">`                 | 文件丢失、权限问题     |
| 字体      | `@font-face` 中引用 URL              | 资源跨域、404          |
| 视频/音频 | `<video src>`、`<audio src>`         | 文件不存在、格式不兼容 |

资源加载失败的原因可以归纳总结为以下几个方面：

1. 路径错误（相对路径/绝对路径不一致）

2. 资源被删除或未部署

3. CDN/服务器宕机或超时

4. 网络断开或慢速加载

5. 资源跨域未配置 CORS

6. 浏览器拦截（如图片安全策略、广告拦截）

### 为什么资源加载失败不会被 `try...catch` 或 `window.onerror` 捕获？

当页面中的资源（如图片、脚本、样式等）加载失败时，这类错误并不属于 JavaScript 执行时的异常，而是浏览器在处理外部资源请求过程中产生的网络或文件级错误。

#### 1. `try...catch` 无法捕获

`try...catch` **只能捕获同步的 JavaScript 执行错误，无法作用于 DOM 元素的加载过程。**

示例：

```js
try {
  const img = new Image();
  img.src = "moment.png"; // 图片加载失败
  // try...catch 不会捕获这个加载失败
} catch (e) {
  console.error("捕获不到图片加载失败"); // 不会执行
}
```

![20250728141356](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250728141356.png)

图片等静态资源的加载过程是由浏览器内部机制（网络层）处理的，属于异步且非 JavaScript 引擎控制的流程。即使资源加载失败，比如图片 404 或 CDN 超时，浏览器只会触发 `error` 事件，而不会抛出 JS 层级的异常。因此，这类错误不会进入 JavaScript 的执行上下文，也就无法通过 `try...catch` 或 `window.onerror` 来捕获。

#### 2. `window.onerror` 捕不到资源错误

`window.onerror` **主要用来捕获 JavaScript 脚本运行时的异常，比如 `ReferenceError` 或 `TypeError`，它不会捕获 HTML** 标签（如 `<img>`、`<script>`、`<link>`）加载资源失败的情况。

只有通过 `<script>` 引入的 JS 文件出错，并且不跨域或带上了 `crossorigin` 且返回了 `Access-Control-Allow-Origin` 头时，才可能进入 `window.onerror`。

##### 3. 怎么捕获这类错误

通过监听 `window` 或 `document` 上的 `error` 事件，并设置为捕获阶段（`true`），才能**捕获资源加载失败事件**。

```js
window.addEventListener(
  "error",
  function (e) {
    if (
      e.target instanceof HTMLImageElement ||
      e.target instanceof HTMLScriptElement ||
      e.target instanceof HTMLLinkElement
    ) {
      console.warn("捕获到资源加载失败：", e.target.tagName, e.target);
    }
  },
  true,
);

const img = new Image();
img.src = "moment.png"; // 图片加载失败
document.body.appendChild(img);
```

## Promise 异常？

在 JavaScript 中，`Promise` 是一种处理异步逻辑的机制。但在异步执行过程中，如果发生了错误（如接口请求失败、手动抛出异常、逻辑错误等），就会产生 Promise 异常。

这些异常如果没有被正确捕获和处理，不仅会导致程序行为异常，还可能在控制台出现 `Uncaught (in promise)` 或 `Unhandled Promise rejection` 警告，甚至导致应用中断。

常见的 Promise 异常场景

| 场景类型        | 说明                                                       | 示例代码                                                       |
| --------------- | ---------------------------------------------------------- | -------------------------------------------------------------- |
| 显式拒绝        | 主动使用 `Promise.reject()` 或 `reject()` 拒绝 Promise     | `Promise.reject("出错了");`                                    |
| 内部抛错        | 在 `.then()` 或构造器中抛出错误                            | `throw new Error("异常");`                                     |
| 异步代码抛错    | 异步回调中抛出错误（如 `setTimeout`），但未使用 `reject()` | `setTimeout(() => { throw new Error('异步异常') });`           |
| 请求失败        | 接口 404、超时、网络异常等                                 | `fetch('/404').then(...).catch(...)`                           |
| 缺少 `.catch()` | 没有添加 `.catch()`，导致异常未被处理                      | `Promise.resolve().then(() => { throw new Error('error'); });` |

### 如何捕获 Promise 异常

#### 1. 使用 `.catch()` 处理异常

```js
fetch("/api/data")
  .then((res) => res.json())
  .then((data) => {
    console.log("请求成功：", data);
  })
  .catch((err) => {
    console.error("请求失败：", err);
  });
```

#### 2. 使用 `async/await` + `try...catch`

```js
async function loadData() {
  try {
    const res = await fetch("/api/data");
    const data = await res.json();
    console.log("获取数据成功：", data);
  } catch (error) {
    console.error("请求异常：", error);
  }
}
```

### 3. 全局兜底监听：`unhandledrejection`

对于未加 `.catch()` 的 Promise 拒绝，可通过以下方式统一捕获并上报：

```js
window.addEventListener("unhandledrejection", function (event) {
  console.error("⚠️ 未捕获的 Promise 异常：", event.reason);
  // event.reason 即 reject 传入的内容或抛出的错误
});
```

> 💡 这是前端异常监控中非常关键的一步，不能漏！

### 常见的 Promise 异常陷阱

#### 1. 异步回调中抛错无法被 catch 捕获

```js
new Promise((resolve, reject) => {
  setTimeout(() => {
    throw new Error("异步中抛出"); // ❌ 不会被 catch 捕获
  }, 0);
}).catch((err) => {
  console.log("不会执行到这里");
});
```

![20250728145117](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250728145117.png)

正确写法应该是用 `reject()` 显式传递错误

```js
new Promise((resolve, reject) => {
  setTimeout(() => {
    reject(new Error("异步异常")); // ✅ 正确捕获
  }, 0);
}).catch((err) => {
  console.log("捕获到了错误：", err.message);
});
```

![20250728145138](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250728145138.png)

### 2. `.then` 中的异常会向下传递到 `.catch()`

```js
Promise.resolve()
  .then(() => {
    throw new Error("链式异常");
  })
  .then(() => {
    console.log("这里不会执行");
  })
  .catch((err) => {
    console.log("成功捕获异常：", err.message);
  });
```

## React 错误捕获

在 React 应用中，错误大致可以分为两类：一类是传统的 JavaScript 运行时错误，如 `TypeError`、`ReferenceError`；另一类则是发生在 React 渲染流程中的错误，比如组件渲染、生命周期钩子中抛出的异常。针对这些“组件级”的错误，React 提供了错误边界（Error Boundary）机制，用于拦截并隔离渲染错误，防止整个组件树崩溃。

React 组件执行过程中的错误阶段如下所示：

| 阶段                | 错误类型                   | 是否可被 ErrorBoundary 捕获 | 推荐处理方式                        |
| ------------------- | -------------------------- | --------------------------- | ----------------------------------- |
| `render()`          | 渲染时抛错（最常见）       | ✅                          | 使用 ErrorBoundary 包裹             |
| `constructor()`     | 构造函数中抛错             | ✅                          | 同上                                |
| 生命周期钩子中      | `componentDidMount` 等报错 | ✅                          | 同上，可在 `componentDidCatch` 上报 |
| 事件回调中          | `onClick` 中抛错           | ❌                          | 必须用 `try...catch` 处理           |
| 异步回调中          | `fetch`、`setTimeout` 等   | ❌                          | `.catch()` / `try...catch` 处理     |
| Hook 执行中         | `useEffect` 抛错           | ❌                          | 自行包裹 `try...catch`              |
| Suspense 懒加载失败 | lazy 组件加载失败          | ✅（需与 Suspense 搭配）    | ErrorBoundary + Suspense            |

### 什么是错误边界（Error Boundary）

错误边界是一个类组件（Class Component），**通过特定生命周期函数来捕获其子组件树中发生的渲染错误，并用降级 UI 替代崩溃内容。**

下面是一个最基础的错误边界组件示例，它通过类组件实现，并在出错时显示备用 UI：

```jsx
import React from "react";

class ErrorBoundary extends React.Component {
  constructor(props) {
    super(props);
    this.state = { hasError: false };
  }

  static getDerivedStateFromError(error) {
    return { hasError: true };
  }

  componentDidCatch(error, info) {
    console.error("捕获到错误：", error, info);
    // 你也可以在这里做错误上报
  }

  render() {
    if (this.state.hasError) {
      return <h2>组件出错了，请稍后再试。</h2>;
    }

    return this.props.children;
  }
}

export default ErrorBoundary;
```

接下来我们可以在我们的页面上直接使用：

```jsx
import "./styles.css";
import ErrorBoundary from "./components/errorboundary";

// 故意制造一个错误组件用于测试
function BrokenComponent() {
  throw new Error("模拟渲染错误");
  return <div>这行永远不会执行</div>;
}

export default function App() {
  return (
    <div className="App">
      <h1>Hello CodeSandbox</h1>
      <ErrorBoundary>
        <BrokenComponent />
      </ErrorBoundary>
    </div>
  );
}
```

## 监听前端报错信息

在前端开发中，如何全局捕获 JavaScript 报错一直是稳定性保障的关键一环。`window.onerror` 和 `window.addEventListener('error')` 是浏览器原生提供的两种错误监听方式，但它们在行为、参数以及适用范围上存在明显差异。

### `window.onerror`

window.onerror 的语法如下所示：

```js
window.onerror = function (message, source, lineno, colno, error) {
  // 处理逻辑
};
```

它接收的参数如下类型图所示：

![20250728151846](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250728151846.png)

最终库归纳为下表：

| 参数名    | 类型       | 描述                                          |
| --------- | ---------- | --------------------------------------------- |
| `message` | string     | 错误信息，如 `"Uncaught TypeError: xxx"`      |
| `source`  | string     | 报错的脚本地址（或文件名）                    |
| `lineno`  | number     | 报错的行号                                    |
| `colno`   | number     | 报错的列号                                    |
| `error`   | Error 对象 | 原始错误对象，包含 `.name` 和 `.stack` 等属性 |

值得注意的是某些浏览器（尤其是跨域脚本）会把这些信息变成 `Script error.`，这是为了防止泄露其他域名上的代码细节，除非你配置了 `crossorigin` + 后端设置 `Access-Control-Allow-Origin`。

### `window.addEventListener('error')`

它的语法如下所示：

```js
window.addEventListener(
  "error",
  function (event) {
    console.log(event);
  },
  true,
);
```

这里的 `event` 是一个标准的 `ErrorEvent` 实例，它比 `onerror` 传的参数更完整、结构更统一。

![20250728153154](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250728153154.png)

它的属性如下所示：

| 属性名                  | 含义说明                                                             |
| ----------------------- | -------------------------------------------------------------------- |
| `isTrusted`             | 表示事件是否是由浏览器自动触发（`true`而非由 JS 手动 `dispatchEvent` |
| `bubbles`               | 是否支持事件冒泡（资源错误是 `false`）                               |
| `cancelable`            | 是否能通过 `preventDefault()` 阻止默认行为（此处是 `false`）         |
| `composed`              | 事件是否可以穿越 shadow DOM                                          |
| `currentTarget`         | 当前正在处理事件的对象（这里是 `null`，因为你是绑定在 `window` 上）  |
| `defaultPrevented`      | 是否已被 `preventDefault()` 调用（没有则是 `false`）                 |
| `eventPhase`            | 当前事件在传播中的阶段（0 = 不在任何阶段）                           |
| `returnValue`           | 旧版属性，与 `preventDefault()` 有关（一般忽略）                     |
| `srcElement` / `target` | 事件的目标对象，这里是 `<img>` 元素本身                              |
| `timeStamp`             | 事件触发的时间戳（单位毫秒）                                         |
| `type`                  | 事件类型，这里是 `"error"`                                           |

### 两者区别

`window.onerror` **是较早的全局错误处理方式，在 JavaScript 报错后立即触发**，返回多个独立参数（如 message、source、lineno 等）。但它无法捕获资源类错误，且只支持一个监听函数，适用范围有限。

相比之下，`addEventListener('error')` **基于标准事件机制，可在捕获阶段监听包括图片、脚本在内的资源加载失败，并支持多个监听器，更适合现代错误监控系统。**

> 简单说：`onerror` 快速处理 JS 错误，`addEventListener` 更通用，JS 和资源错误都能收。

## 总结

前端错误主要包括语法错误、运行时错误、资源加载失败、异步异常和框架内部错误等。常见的捕获方式有 `try...catch`、`window.onerror`、`window.addEventListener('error')` 以及 `unhandledrejection` 等，不同场景适用方式不同。

对于 React 等框架，还可以通过**错误边界**组件捕获渲染过程中的异常。现代前端项目建议结合本地捕获 + 全局监听 + 错误上报，实现完整的错误监控体系。最终目标是：提前发现问题，精准定位，保障用户体验。
