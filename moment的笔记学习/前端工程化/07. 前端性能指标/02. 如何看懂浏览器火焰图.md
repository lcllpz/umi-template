让我们从 `perf` 命令讲起，它是 Linux 系统原生的性能分析工具，`perf` 是 "performance" 的缩写。这个工具可以帮助我们了解 CPU 正在执行哪些函数，并记录 调用栈（stack trace），从而诊断程序的性能瓶颈。

在默认配置下，`perf` 的采样频率为 99Hz，即每秒抽样 99 次。如果在某一秒内，99 次采样全部落在同一个函数上，说明 CPU 在这一秒几乎都在运行这段函数代码，可能存在性能问题。

下面是一个典型的使用命令：

```bash
sudo perf record -F 99 -p 13204 -g -- sleep 30
```

各参数含义如下：

- `perf record`：开始采样并记录数据
- `-F 99`：设置采样频率为每秒 99 次
- `-p 13204`：指定要分析的进程 ID（即 PID 为 13204 的进程）
- `-g`：采集函数调用栈信息
- `-- sleep 30`：采样持续时间为 30 秒

执行该命令后，`perf` 会生成一个 `.data` 文件，里面包含了详细的采样记录。以一台 16 核 CPU 的服务器为例，30 秒内每核每秒采样 99 次，将会产生约 47,520 个调用栈记录，总量可能达到几十万甚至上百万行。

为了更方便地阅读分析这些数据，可以使用如下命令生成汇总报告：

```bash
sudo perf report -n --stdio
```

这个结果还是不易读，所以才有了火焰图。

该命令会统计每个函数调用栈出现的频率，并按照占比从高到低排序，帮助我们快速定位哪些函数最消耗 CPU 时间。

### Main

每个渲染进程（tab）都有一个主线程，并且主线程非常繁忙，既要处理 DOM，又要计算样式，还要处理布局，同时还需要处理 JavaScript 任务以及各种输入事件。

X 轴代表着事件。每个长条代表着一个 event。长条越长就代表这个 event 花费的时间越长。

Y 轴代表了调用栈（call stack）。在栈里，上面的 event 调用了下面的 event。

这些事件其实对应着浏览器的渲染过程：

![20250723115521](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250723115521.png)

当渲染首屏时，浏览器分别解析 HTML 与 CSS 文件，生成文档对象模型（DOM）与样式表对象模型（CSSOM）；合并 DOM 与 CSSOM 成为渲染树（Render Tree）；计算样式（Style）；计算每个节点在屏幕中的精确位置与大小（Layout）；将渲染树按照上一步计算出的位置绘制到图层上（Paint）；渲染引擎合成所有图层最终使人眼可见（Composite Layers）。

#### 举个例子

首先我们准备这样的一段代码：

```
<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <title>worker performance optimization</title>
  </head>
  <body>
    <script>
      function a() {
        b();
      }
      function b() {
        let total = 0;
        for (let i = 0; i < 10 * 10000 * 10000; i++) {
          total += i;
        }
        console.log("b:", total);
      }

      a();
    </script>
    <script>
      function c() {
        d();
      }
      function d() {
        let total = 0;
        for (let i = 0; i < 1 * 10000 * 10000; i++) {
          total += i;
        }
        console.log("c:", total);
      }
      c();
    </script>
  </body>
</html>
```

在上面的代码中，两个 script 标签是两个宏任务，第一个宏任务的调用栈是 a、b，第二个宏任务的调用栈是 c、d。

当我们打开 Performance 一看，丸辣，这么段的一段代码居然要执行这么久：

![20250723134657](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250723134657.png)

主线程持续运行着 `Event Loop`，可以观察到它依次处理了两个宏任务（Task），其调用栈分别对应函数链 `a → b` 和 `c → d`，正好与我们编写的代码相符。期间虽然还包含了浏览器内部的操作，如 `Parse HTML`、`Evaluate Script` 等，但这些属于底层执行过程，我们可以在分析中略去不计。

Performance 工具的核心在于分析主线程的 Event Loop，重点关注每个宏任务（Task）的耗时、调用栈等关键信息。

当你点击某个宏任务后，下方的面板会展示其详细的调用栈信息。你可以通过切换视图来辅助分析：

- Bottom-Up：以函数耗时排序，方便定位最耗资源的函数；

- Call Tree：以调用关系为主，以树状结构展示函数的调用路径。

![20250723140434](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250723140434.png)

每个函数的耗时也都显示在左侧，右侧有源码地址，点击就可以跳到 Sources 对应的代码。

每个函数的耗时会显示在左侧，便于快速识别性能热点；右侧则显示该函数在源码中的位置，点击即可跳转到 DevTools 中 `Sources` 面板的对应代码行，方便进一步排查与优化。

![20250723141313](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250723141313.png)

每行代码的耗时都被直接展示出来，非常直观，极大地方便了性能分析！

工具了解完之后，我们来具体分析这段代码的性能瓶颈：

很明显，`b` 和 `d` 两个函数中的循环累加操作耗时过高，是主要的性能热点。在 Performance 面板中，你也可以看到对应的 Task 被标记为红色，说明浏览器已经识别它们为 长任务（Long Task）。

此外，下方的 Summary 面板 也明确给出了 Long Task 的警告提示，进一步印证了这些同步计算严重阻塞了主线程。

![20250723141607](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250723141607.png)

我们这次的优化目标，是将两个 Long Task 中耗时严重的逻辑（即循环累加）去除或拆分成多个更小的任务，以减轻主线程的负担。

关于“拆分任务”这一点，可以类比 React 的优化策略 —— 从递归渲染 Virtual DOM 转向可中断的 Fiber 架构，本质上也是为了将大任务拆分为多个可调度的小任务，避免阻塞主线程。

不过很显然，我们当前的这两个循环逻辑本身就非常紧凑、没有明确的拆分点，也不涉及可中断的阶段性操作。因此，拆分任务的方案在这里并不适用。

那还有没有别的办法？答案是肯定的 —— 我们可以尝试将这段耗时逻辑从主线程中“挪出去”，交给浏览器提供的 Web Worker 来处理。

Web Worker 的设计初衷之一，就是将计算密集型任务转移到独立线程中执行，避免阻塞主线程，从而提升页面的流畅度与响应性，非常适合当前这种纯计算型的性能瓶颈。

```js
<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <title>worker performance optimization</title>
  </head>
  <body>
    <script>
      // 创建两个独立 Worker
      const workerB = new Worker("workerB.js");
      const workerD = new Worker("workerD.js");

      // 调用函数 a → b（交给 workerB）
      function a() {
        b();
      }
      function b() {
        workerB.postMessage("start");
      }

      // 调用函数 c → d（交给 workerD）
      function c() {
        d();
      }
      function d() {
        workerD.postMessage("start");
      }

      // 监听 workerB 结果
      workerB.onmessage = function (e) {
        console.log("b:", e.data.total);
      };

      // 监听 workerD 结果
      workerD.onmessage = function (e) {
        console.log("d:", e.data.total);
      };

      // 执行流程
      a();
      c();
    </script>
  </body>
</html>
```

现在我们都把我们的计算都放在了 worker 中去处理，在前面的内容中，我们看到了，每次解析 html 的时候都是一个长任务，这是因为一些插件的影响，现在我们先打开正常的模式：

![20250723143434](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250723143434.png)

但是你会发现后面的两个 Long Task 没有了，但是前面还有一个，现在只要我们开启无痕模式，这样性能分析就不会受影响了：

![20250723143704](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250723143704.png)

你会发现，主线程中已经没有 Long Task 了。同时，在 Main 线程下方出现了两个新的 Worker 线程 —— 尽管它们各自仍有耗时较长的任务，但这并不会影响主线程的流畅性。

毕竟这些计算本身就比较重，只要它们不阻塞主线程，就不会影响页面的交互体验。

通过将计算任务拆分到 Worker 中执行，我们不仅解决了主线程的 Long Task 问题，还充分利用了浏览器的多线程能力（底层多核 CPU 支持），从而显著提升了页面的响应性和整体性能。

## 总结

Chrome DevTools 的 Performance 工具 是进行网页性能分析的强大利器。它能够详细记录代码的执行过程，包括主线程中的各个任务（Task）、每个函数的调用关系与耗时，还可以精准定位到 Sources 面板中的对应源码行，帮助开发者快速识别性能瓶颈。

性能优化的核心目标是识别并消除页面中的 长任务（Long Task）。因为浏览器的渲染流程和 JavaScript 执行共享主线程，任何耗时操作都会阻塞页面渲染，影响用户体验。

在这次真实的优化案例中，我们借助 Performance 工具定位到一段高耗时的计算逻辑。为了解决这一问题，我们将这部分计算拆分到 Web Worker 中执行，从而将任务从主线程中剥离，充分利用多核 CPU 的并行能力，最终成功消除了主线程中的长任务，实现了页面性能的显著提升。
