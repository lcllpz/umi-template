浏览器缓存分为 `强缓存` 和 `协商缓存` 两种机制。**强缓存可直接使用本地资源，无需向服务器发送请求，提升加载速度；协商缓存则需与服务器确认资源是否更新，未更新则返回 304 状态码继续使用缓存。**

合理利用缓存可以显著提升页面性能、减少服务器压力和带宽消耗，同时支持离线访问，优化用户体验。

## 浏览器缓存，那它到底是缓存在哪里？

浏览器缓存主要存储在内存和磁盘中，不同机制决定其位置和生命周期，常见缓存方式包括以下几种：**`(浏览器自己的存储调度)`**

### 内存缓存

内存缓存是将资源存储在浏览器的 RAM 中，具有读取速度快的优势，适合当前页面中频繁访问的资源，如 CSS、图片等。由于**内存缓存的生命周期较短，通常在`页面刷新或关闭后就会失效`，而且受限于内存容量，不适合
存储体积较大的文件**。它主要用于提升当前会话中的资源加载效率。

![20250730142336](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250730142336.png)

打开浏览器 `Network` 面板，查看资源加载的 `Size` 列，显示` memory cache` 说明命中内存缓存。

### 磁盘缓存

磁盘缓存是将资源`存储在本地硬盘中，容量较大，适合缓存体积较大的静态资源`，如视频、字体等。它支持跨页面访问，`即使浏览器关闭或重启后，仍可继续使用缓存内容`。**虽然访问速度略慢于内存缓存，但磁盘缓存的生命周期更长，更适用于需要长期复用的资源。**

![20250730142513](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250730142513.png)

打开浏览器 `Network` 面板，查看资源加载的 `Size` 列，显示 `disk cache` 说明命中磁盘缓存。

### Service Worker

`Service Worker` **是浏览器在后台运行的一段独立脚本，脱离网页主线程，具备拦截网络请求、管理缓存、实现离线访问等能力**，是构建 PWA（渐进式 Web 应用）的核心技术之一。

`它本质上充当浏览器与网络之间的“可编程代理层”，可对资源请求做出响应，决定是从网络获取还是直接返回本地缓存，完全由开发者控制。`

通过这种机制，开发者可以实现更灵活的缓存策略、提升页面性能，并为用户提供稳定的离线体验。

它的工作流程如下步骤所示：

1. 注册 Service Worker：网页首次加载时注册 Service Worker 脚本。

2. 安装（install）事件：Service Worker 被下载后，触发 install 事件，通常在此阶段缓存静态资源。

3. 激活（activate）事件：安装完成后进入激活阶段，可用于清理旧缓存。

4. 拦截请求（fetch）：页面发起的网络请求会被 Service Worker 拦截，开发者可决定返回缓存还是重新请求。

接下来我们编写 Service Worker 代码：

```js
const CACHE_NAME = "image-cache-v1";
const IMAGE_URLS = [
  "https://cdn.pixabay.com/photo/2025/04/30/13/05/cat-9569386_1280.jpg",
  "https://cdn.pixabay.com/photo/2025/06/19/16/21/adventure-9669329_640.jpg",
];

// 安装阶段：预缓存选定的图片
self.addEventListener("install", (event) => {
  event.waitUntil(
    caches.open(CACHE_NAME).then((cache) => {
      return cache.addAll(IMAGE_URLS);
    }),
  );
});

// 拦截请求：优先从缓存获取
self.addEventListener("fetch", (event) => {
  if (IMAGE_URLS.includes(event.request.url)) {
    event.respondWith(
      caches.match(event.request).then((res) => {
        return res || fetch(event.request);
      }),
    );
  }
});
```

这段 `sw.js` 是一个用于缓存图片的 Service Worker 脚本，在安装阶段会预先下载并缓存指定的两张图片。之后，当页面请求这些图片时，Service Worker 会拦截请求并优先从缓存中返回资源，如果缓存中没有则从网络获取。这样可以加快加载速度并支持离线访问。

### DNS 缓存

DNS 缓存存在多个层级，包括浏览器、操作系统、路由器以及 ISP，在不同阶段帮助加快域名解析速度。为了进一步优化性能，可以使用 DNS 预解析（`dns-prefetch`）在页面加载前提前解析域名，减少首次请求延迟：

```
<link rel="dns-prefetch" href="//example.com" />
```

### 预加载与预解析（Preload / Prefetch / Preconnect）

现代浏览器提供多种预加载机制，用于提升页面加载性能：

`preload`：用于加载当前页面中关键且立即需要的资源

```
<link rel="preload" href="style.css" as="style" />
```

`prefetch`：用于提前加载未来可能使用的资源（如下一页脚本）

```
<link rel="prefetch" href="next-page.js" />
```

`preconnect`：用于提前建立连接（DNS、TLS、TCP），减少请求延迟

```
<link rel="preconnect" href="https://example.com" />
```

浏览器会根据资源的类型、使用时机和策略决定其缓存方式。合理使用这些指令可有效提升首屏加载速度和整体用户体验。

## 强缓存和协商缓存

> **内存缓存与磁盘缓存时`存储的方式`；强缓存和协商缓存时存储的`使用策略`**,两个不一样

除了上面介绍的几种缓存方式，浏览器还有两种非常常见且基础的缓存机制：`强缓存` 和 `协商缓存`。**它们基于 HTTP 协议，通过响应头控制资源是否使用本地缓存或重新向服务器发起请求，是浏览器默认支持的缓存逻辑**，对于理解网页加载流程和性能优化非常有帮助。

首先我们先栏看强缓存和协商缓存的工作流程图，如下所示：

![20250730152245](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250730152245.png)

如果还是太好理解的话再加上这张图来：

![20250313084715](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250313084715.png)

当浏览器请求资源（如 HTML、CSS、JS、图片等）时，会先检查缓存，决定是直接使用缓存还是向服务器请求新资源。整个缓存机制主要分为 `强缓存` 和 `协商缓存` 两种策略。

### 强缓存（Freshness）

强缓存是指浏览器在本地缓存未过期的情况下，直接使用缓存资源，不向服务器发送请求，从而加快页面加载速度。

浏览器通过响应头中的 `Cache-Control` 或 `Expires` 判断缓存是否仍然有效：

- `Cache-Control: max-age=3600`：表示资源在 3600 秒内有效，可直接使用。

- `Expires: Wed, 21 Oct 2025 07:28:00 GMT`：设定资源的绝对过期时间，若当前时间未超过，则命中缓存。

**当浏览器请求资源时，如果缓存仍在有效期内，会直接从本地读取，无需向服务器发送请求。一旦缓存过期，浏览器会进入协商缓存阶段，通过条件请求与服务器确认资源是否更新。这样既提升了性能，又保证了资源的时效性。**

### 协商缓存（Revalidation）

当强缓存失效后，浏览器不会立刻重新下载资源，而是向服务器发送 `条件请求`，确认资源是否发生变化。如果服务器判断资源未更新，就会返回 `304 Not Modified`，浏览器即可继续使用**本地缓存(使用磁盘的缓存或者内存中的缓存资源)**，节省流量和加载时间。

它的请求流程图如下所示：

![20250730153507](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250730153507.png)

> **资源首次请求响应时，服务器可同时返回 Cache-Control或者Expires 强缓存字段 和 ETag或者Last-Modified 协商缓存标识；浏览器先依据强缓存有效期直接使用本地缓存，过期后自动携带对应标识发起协商请求，由服务器返回 304 决定是否复用本地资源。**
> ![alt text](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/images202507301535071.png)

`ETag`（实体标签）是由服务器生成的资源唯一标识符，通常基于资源内容的哈希值计算得出。只要资源内容发生变化，`ETag` 就会随之更新，用于精确判断资源是否被修改。

下面是一个完整的 ETag 协商缓存示例，包含一个用于请求资源的 HTML 页面，以及一个使用 Express 搭建的服务端，通过手动设置 `ETag` 来实现缓存验证逻辑。用户每次点击按钮请求资源时，服务器会根据 ETag 判断资源是否修改，从而决定返回新内容或 304 状态码。这个示例直观演示了协商缓存的工作机制。

首先我们编写一个 HTML 文件：

```js
<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <title>ETag 协商缓存示例</title>
  </head>
  <body>
    <h1>ETag 缓存测试</h1>
    <button onclick="loadFile()">加载资源</button>
    <pre id="output"></pre>

    <script>
      function loadFile() {
        fetch("/file.txt")
          .then((res) => {
            document.getElementById("output").textContent =
              `状态码: ${res.status}\n\n` +
              `ETag: ${res.headers.get("etag")}\n\n`;

            return res.text();
          })
          .then((text) => {
            document.getElementById("output").textContent += `内容:\n${text}`;
          })
          .catch((err) => console.error(err));
      }
    </script>
  </body>
</html>
```

紧接着我们再编写一个内容的文件，存放在 `public/file.txt` 目录下，之后我们再编写我们的 NodeJs 服务：

```js
const express = require("express");
const fs = require("fs");
const path = require("path");
const crypto = require("crypto");

const app = express();
const PORT = 3000;

// 提供静态文件访问 index.html
app.use(express.static(__dirname));

// 手动处理 file.txt 的请求，添加 ETag 协议
app.get("/file.txt", (req, res) => {
  const filePath = path.join(__dirname, "public", "file.txt");
  const fileContent = fs.readFileSync(filePath, "utf-8");

  // 根据文件内容生成 ETag（也可以用文件时间戳或 hash）
  const etag = crypto.createHash("md5").update(fileContent).digest("hex");

  // 对比请求头里的 If-None-Match
  if (req.headers["if-none-match"] === etag) {
    res.status(304).end(); // 不返回内容
  } else {
    res.setHeader("ETag", etag);
    res.setHeader("Content-Type", "text/plain");
    res.send(fileContent);
  }
});

app.listen(PORT, () => {
  console.log(`Server running at http://localhost:${PORT}`);
});
```

### Last-Modified 协商缓存机制

当服务器未启用 `ETag` 时，浏览器会退而使用 `Last-Modified` 进行基于时间的缓存验证。这个时间的和 ETag 的处理流程差不多：

1. 服务器首次返回资源时，会在响应头中附带资源的最后修改时间：

```
Last-Modified: Tue, 12 Mar 2024 10:00:00 GMT
```

2. 浏览器缓存资源后，下一次请求会在请求头中携带：

```
If-Modified-Since: Tue, 12 Mar 2024 10:00:00 GMT
```

服务器收到请求后会比较 `If-Modified-Since` 中的时间与资源的最后修改时间。若资源未变则返回 `304`，浏览器继续使用缓存；否则返回 `200` 并提供更新后的内容。

## 不同刷新操作方式，对强制缓存和协商缓存的影响

当用户进行普通刷新（如 F5 或点击刷新按钮）时，浏览器会先检查强缓存是否仍有效，若未过期则直接使用本地缓存；若已过期，则通过协商缓存发送条件请求与服务器确认资源是否更新。若资源未变，返回 `304` 使用缓存，否则返回 `200` 并更新资源。这种方式对服务器负担较小。

强制刷新（如 Ctrl+F5 或 Shift+刷新）则会跳过所有缓存，直接向服务器请求最新资源，也不会携带协商缓存信息，所有资源都重新下载，服务器压力最大。

使用地址栏回车访问页面时，行为与普通刷新相似，优先使用强缓存，失效后触发协商缓存，整体请求逻辑一致，服务器负担适中。

在浏览器执行前进或后退操作时，页面通常直接从内存缓存中恢复，不发起网络请求，即便资源已过期也可能继续使用，是最轻量的缓存方式。

若用户清空缓存后刷新，由于本地没有任何可用缓存，也无法进行协商，浏览器会重新请求所有资源，等同于首次访问，服务器负担最大。

## 总结

强缓存是指浏览器在资源未过期时，直接使用本地缓存，不与服务器通信，由 `Cache-Control` 或 `Expires` 控制。

协商缓存则在强缓存失效后，通过请求头（如 `If-None-Match` 或 `If-Modified-Since`）与服务器验证资源是否更新。若资源未变，服务器返回 `304`，浏览器继续使用缓存；若已更新，则返回新资源并替换本地缓存。

两者结合使用，可以在保证性能的同时，确保资源的时效性与准确性。
