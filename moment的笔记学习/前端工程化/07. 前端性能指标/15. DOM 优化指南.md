在前端开发中，DOM 是连接 JavaScript 与页面展示的桥梁。每一次对 DOM 的操作，都会像交“过桥费”一样，付出一定的性能成本。这个成本可能体现在布局计算、样式重排、甚至是页面的重新渲染上。

因此，理解 DOM 为什么“慢”，是提升页面性能的关键起点。本节将围绕这个问题展开，从 DOM 的运行机制入手，分析性能瓶颈出现的根本原因，并提出一套系统的优化思路，帮助我们以更高效的方式与 DOM 打交道。

## 为什么 DOM 这么慢？

### 因为收了“过路费”

> 可以将 DOM 和 JavaScript 想象成两个各自独立的小岛，它们之间通过一座“收费桥梁”相连。——《高性能 JavaScript》

JavaScript 的执行速度非常快，在 JS 内部操作对象、计算数据时通常毫无压力，甚至修改 DOM 对象的引用也很快。但真正的 DOM 操作并不是 JS 自己就能完成的，它其实是一场跨模块的协作。

**这是因为 JavaScript 引擎与浏览器的渲染引擎是彼此独立的系统。当我们用 JS 操作 DOM 时，实际上是 JS 引擎与渲染引擎之间的一次“跨界通信”**。这项通信依赖一套桥接接口——可以将它形象地比作一座连接两个系统的桥梁（如下图）。

![20250730124150](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250730124150.png)

而“过桥”是要付出代价的。每当我们访问或修改 DOM，都必须穿越这座桥，进行一次跨引擎的调用。这种通信不是零成本的，它可能涉及数据转换、状态同步等隐性开销。

当这样的操作频繁发生时，性能问题就会逐渐显现。这也正是为什么我们总强调要“减少 DOM 操作”——这是优化性能的关键之一，而不是一种无的放矢的建议。

### 对 DOM 的修改引发样式的变更

我们说过，跨“桥”操作 DOM 是有成本的，而到达“桥”的另一端，浏览器还要付出额外的代价来响应这些更改。

很多时候，我们修改 DOM 的目的并不是单纯访问，而是改变它的样式或结构。这些修改如果影响了页面的视觉呈现，就会触发浏览器的 `回流（Reflow）`或 `重绘（Repaint）`。

这个过程的本质，是我们对 DOM 的改动触发了渲染树（Render Tree）的更新：

![20250730124745](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250730124745.png)

- 回流（Reflow）：当修改影响了元素的几何属性（如宽度、高度、位置或显示状态）时，浏览器必须重新计算布局，确定所有相关元素的位置和尺寸。这一过程是代价最高的，因为它可能影响整棵渲染树。

- 重绘（Repaint）：当修改只影响元素的视觉样式（如颜色、背景色、字体等），但不改变其几何属性时，浏览器会跳过布局计算，直接进行样式更新和重新绘制。

可以总结为一句话：

> 回流一定会引发重绘，而重绘不一定涉及回流。

二者相比，回流的开销更大，因为它涉及布局计算和可能的多次 DOM 遍历。但无论哪一种，都会影响性能，都是我们开发中要尽量避免频繁触发的“隐形成本”。

因此，优化页面性能的一项关键策略就是：减少回流和重绘的频率与范围，让浏览器少做不必要的事。

## 如何优化 DOM

知道了 DOM 慢的原因，我们就可以对症下药了。

### 减少 DOM 操作：避开“过路费”，减轻渲染负担

我们来看一个 🌰，HTML 内容如下：

```js
<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <meta http-equiv="X-UA-Compatible" content="ie=edge" />
    <title>DOM操作测试</title>
  </head>
  <body>
    <div id="container"></div>
  </body>
</html>
```

现在有个假设需求 —— 我们需要向 `container` 元素中插入一万句相同的话。如果你这样写：

```javascript
for (var count = 0; count < 10000; count++) {
  document.getElementById("container").innerHTML +=
    "<span>我是一个小测试</span>";
}
```

表面上代码简单直观，但它有两个明显的性能隐患。

#### ☝️ 问题一：过路费交太多

每一次循环都调用 `document.getElementById("container")`，等于每次都跨越 JS 和渲染引擎之间的“桥接接口” —— 也就是每次都交了一次“过路费”。这样就交了 10000 次，但其实只有第一次是必要的，剩下 9999 次完全可以避免。

优化方式：缓存 DOM 引用

```javascript
let container = document.getElementById("container");
for (let count = 0; count < 10000; count++) {
  container.innerHTML += "<span>我是一个小测试</span>";
}
```

#### ✌️ 问题二：频繁触发渲染

每次循环都对 `innerHTML` 进行更新，会导致 DOM 树被修改 10000 次，每一次修改都可能引发重绘甚至回流，这是巨大的性能浪费。

优化方式：先处理内容，最后一次性写入 DOM

```javascript
let container = document.getElementById("container");
let content = "";
for (let count = 0; count < 10000; count++) {
  content += "<span>我是一个小测试</span>";
}
container.innerHTML = content;
```

这种做法背后的原则就是“JS 的事，JS 自己搞定，搞定了再找 DOM 报告”。这其实就是我们常说的 —— 让 JS 给 DOM 分担压力。

#### 更进一步：用 `DocumentFragment` 优雅优化

这个优化思路在 [`DocumentFragment`](https://developer.mozilla.org/zh-CN/docs/Web/API/DocumentFragment) 中体现得更为彻底。

> `DocumentFragment` 是一个脱离 DOM 树的轻量级文档容器。它允许你批量构建节点结构，并在插入真实 DOM 时一次性“交付”，整个过程不会引发多次渲染。

在上面的例子中，我们用字符串缓存中间结果，其实就已经在做“分离构建”。而 `DocumentFragment` 提供了更结构化、更 DOM 原生的方式来达成同样的目标：

```javascript
let container = document.getElementById("container");
let content = document.createDocumentFragment(); // 创建一个“虚拟容器”

for (let count = 0; count < 10000; count++) {
  let oSpan = document.createElement("span");
  oSpan.innerHTML = "我是一个小测试";
  content.appendChild(oSpan); // 将节点添加进 fragment
}

container.appendChild(content); // 一次性将 fragment 插入真实 DOM
```

`DocumentFragment` 就像一个脱离真实 DOM 的“临时容器”，你可以像操作普通 DOM 一样调用 API（如 `appendChild`），但它本身不会触发回流或重绘。最终插入时，它会把内部子节点一次性搬入页面，自己则悄然“隐退”，结构清晰、语义明确，因此在 Vue、jQuery 等主流框架中被广泛应用。

![20250730125354](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250730125354.png)

频繁直接修改 DOM 会导致重复渲染，而拼接字符串或使用 DocumentFragment 则能将渲染合并，显著优化性能。

虽然这个小例子无法概括 DOM 操作的全部性能陷阱，但希望你能掌握一个核心思想：

> 减少 DOM 操作次数，将 JS 层面的处理“提前”完成，统一批量提交。

这是前端性能优化中最常见也最有效的策略之一。

### 事件优化

JavaScript 的事件机制虽然强大，但若使用不当，可能导致性能问题，例如绑定过多事件、频繁触发高频事件（如 scroll、mousemove、resize）或重复绑定造成内存泄漏。事件优化的核心**目标是：在不影响交互体验的前提下，尽可能减少事件处理次数和绑定数量，降低浏览器负担。**

**事件冒泡**机制允许子元素的事件向上传递，因此我们可以只在父元素上绑定一次事件，通过 `event.target` 判断具体是哪个子元素触发的。它的优势在于大幅减少事件绑定数量，并且对动态添加的子元素同样有效，无需额外绑定。

如下所示的 HTML 结构中，多个 `<li>` 子元素都需要响应点击事件：

```
<ul id="list">
  <li>item 1</li>
  <li>item 2</li>
  <li>item 3</li>
</ul>
```

与其在每个 `<li>` 上分别绑定事件，我们可以借助事件冒泡机制，将点击事件统一绑定在父元素 `<ul>` 上，通过判断事件目标实现代理处理：

```js
document.getElementById("list").addEventListener("click", function (e) {
  if (e.target.tagName === "LI") {
    console.log("点击了：", e.target.innerText);
  }
});
```

这种方式不仅减少了事件绑定数量，也能自动处理后续动态添加的子元素，性能与可维护性更佳。

## 总结

DOM 优化的核心在于减少与真实 DOM 的直接交互频率，降低渲染引擎的负担。通过缓存 DOM 引用、合并批量操作、使用 `DocumentFragment` 等离线构建容器，可以有效减少回流与重绘带来的性能开销。

同时，合理应用事件委托和节流/防抖等事件优化技巧，也能避免高频事件拖慢页面响应。最终目标是：让 JS 做更多准备工作，只把最终结果交给 DOM 一次性处理，以提升页面整体性能与流畅度。
