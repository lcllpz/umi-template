## 什么是 INP

INP（Interaction to Next Paint） 是衡量网页整体**交互响应性能的关键指标**，用于评估用户操作后浏览器提供首帧视觉反馈的速度。它关注的不是整个交互逻辑的完成时间，而是从用户触发操作（如点击、点按或键盘输入）开始，到浏览器绘制响应帧为止的延迟。这个过程决定了用户是否能“及时看到”页面的反馈。

![alt text](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/inp.webp)

INP 会记录整个访问过程中的所有交互事件，并从中选取表现最差（排除离群值）的一次作为最终评分，代表该页面在真实使用中的最差交互体验。一次完整交互可能包含多个事件（如 `pointerdown`、`click` 等），由 JavaScript、CSS 或内置控件触发。交互延迟从事件开始到下一帧绘制之间的时间即为 INP 的衡量范围。

如果 INP 值偏高，意味着用户在操作后页面长时间无响应，体验明显“卡顿”。因此，开发者应尽早提供视觉反馈（如加载指示、按钮状态变化等），即使逻辑尚未完成，也能显著提升响应感知和交互体验。

### INP 得分怎样才算理想？

由于用户设备性能差异较大，INP（Interaction to Next Paint）无法一概而论地定义“好”或“坏”。但为了鼓励开发者提升交互响应体验，Web 性能指标推荐使用第 75 百分位（P75）作为评估标准，分别针对移动和桌面用户进行划分。

推荐的 INP 判定标准如下：

- INP ≤ 200ms：交互响应优秀，体验流畅；

- 200ms < INP ≤ 500ms：响应有待优化，可能存在轻微延迟感；

- INP > 500ms：响应明显迟缓，需优先进行性能优化。

这一阈值有助于开发者在不同设备和网络环境下制定切实可行的优化目标，提升整体用户体验。

![20250727094633](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250727094633.png)

良好的 INP 值应不超过 200 毫秒。差的值大于 500 毫秒。

### 互动中包含哪些内容？

互动生命周期。在事件处理脚本开始运行之前，会发生输入延迟，这可能由主线程上的长时间任务等因素导致。然后，系统会运行互动事件处理脚本回调，并在显示下一个帧之前发生延迟。

![20250727094903](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250727094903.png)

网页的互动性通常由 JavaScript 驱动，但浏览器同样支持通过非 JS 控件（如复选框、单选按钮、CSS 控件）实现交互行为。

在 INP 的定义中，系统只关注以下三类用户操作：

- 鼠标点击

- 触摸设备上的点按

- 键盘上的按键输入（实体或屏幕键盘）

这些交互可以发生在主文档中，也可能嵌套于 `<iframe>` 中，例如点击嵌入视频的播放按钮。由于用户感知不到 iframe 的存在，INP 也必须在 iframe 中采集，以全面反映整页体验。不过，由于 JavaScript 无法直接访问跨源 iframe 的事件数据，这也可能导致 CrUX（公共体验数据）与 RUM（私有监测）之间存在差异。

一个完整的交互由多个事件组成，例如一次按键操作会触发 `keydown`、`keypress`、`keyup`；点按则包括 `pointerdown` 和 `pointerup`。其中耗时最长的事件会决定该次交互的总延迟，对 INP 值的贡献最大。

![20250727095141](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250727095141.png)

如图所示，一次用户交互可能由多个事件组成，例如点击操作会包含 `pointerdown`、`click` 等事件。每个事件都有输入延迟（Input delay）、处理时长（Processing duration）和展示延迟（Presentation delay）。INP 取的是整次交互中最长事件的延迟时间，用于衡量页面响应交互的速度。

最终，INP 会在用户关闭页面时计算得出，表示该页面在整个访问周期中的最差交互表现。INP 越低，说明网页在用户操作后越能及时反馈，从而提供更流畅、可靠的交互体验。

### INP 与 First Input Delay (FID) 有何不同？

`INP（Interaction to Next Paint）` 是 `FID（First Input Delay）` 的升级版指标。虽然两者都用于衡量网页响应速度，但它们关注的范围不同：

- FID 仅衡量首次用户交互的输入延迟，主要反映页面加载初期的响应性能；

- INP **则全面记录整个页面生命周期中所有交互的响应时间，从用户触发事件到浏览器完成绘制首帧反馈，反映页面的整体交互性能。**

简而言之：FID 注重首次印象，而 INP 更关注长期体验的稳定性和一致性。这使得 INP 成为评估真实用户交互体验更准确、全面的响应指标。

### 如果未报告 INP 值，该怎么办？

在某些情况下，网页可能不会产生 INP（Interaction to Next Paint）指标值。常见原因包括：

- 用户未进行任何可测量的交互（如点击、点按或按键），即页面加载后无实际操作；

- 用户只进行了不计入 INP 的交互，例如滚动页面或鼠标悬停；

- 页面是由爬虫或无头浏览器访问，这些工具不会模拟真实用户交互行为。

遇到这类情况并不意味着网页性能异常，只是说明用户行为未触发可用于 INP 衡量的事件。

## 如何衡量 INP

INP 既可以在现场测量，也可以在实验室测量，只要我们能模拟真实的用户互动。

### 在现场

理想情况下，应优先基于真实用户监控（RUM）的数据来优化 INP。RUM 不仅能提供网页的 INP 值，还能附带丰富的上下文信息，例如是哪一次交互触发了高延迟、是否发生在加载期间、交互类型（点击、点按或键盘输入）、响应过程的时间分布等。这些细节对于精确定位响应瓶颈极为关键。

如果您的网站符合纳入 [Chrome 用户体验报告（CrUX）](https://developer.chrome.com/docs/crux/) 的条件，您可以通过以下工具快速获取 INP 的实测数据：

- [PageSpeed Insights 中的 CrUX](https://pagespeed.web.dev/)

- 或其他 [Core Web Vitals 工具](https://web.dev/articles/vitals-tools)

这些工具至少能提供页面在来源级别的 INP 分析，部分情况下还可获取到具体网址级的性能数据。

⚠️ 需要注意的是：CrUX 只能告诉你“是否存在问题”，但无法说明问题出在哪里。相比之下，RUM 解决方案可将高 INP 值精确归因于具体用户、页面和交互行为，避免了盲目猜测和无效优化。

### 实验室

在优化 INP 前，应优先参考真实用户数据，有助于准确定位哪些交互存在响应延迟。现场数据明确问题后，再通过实验室工具复现和调试会更高效。

如果没有实地数据，也可借助实验室测试，但需注意：INP 的结果依赖测试过程中是否执行了有效交互。部分工具仅模拟加载流程，无法生成 INP，这时可暂以 TBT（总阻塞时间） 作为参考，虽不等同，但能反映主线程的繁忙程度。

在实验环境中复现问题，可采用以下策略：

- 模拟典型用户路径（如点击、表单、菜单等）

- 聚焦页面加载初期的交互，主线程最易阻塞

- 避免仅依赖工具默认行为，主动触发交互更可靠

## 如何提高 INP

一旦确认某次交互存在响应缓慢，并且能在实验室中手动复现，下一步就需要针对交互的各个阶段进行优化。一次完整的交互延迟主要由三部分构成：

1. 输入延迟：从用户发起操作到事件回调开始执行的等待时间

2. 处理时长：事件处理函数的实际执行时间

3. 呈现延迟：浏览器将视觉反馈绘制到屏幕上的时间

这三者的总和，就是该交互的 总延迟时间（即 INP 值）。每个环节都可能成为瓶颈，因此优化时要分别针对它们进行分析和改进。

⚠️ 注意：每个浏览上下文（如页面或 iframe）都有独立的主线程。
虽然 INP 是在页面级别统计的，但它包含了主文档及其所有嵌套 iframe 的交互延迟。如果交互出现在 iframe 中，请确认具体是在主线程还是子线程执行，以便定位和优化。

此外，在设备性能受限的情况下，即便线程独立，资源争用也可能造成相互影响，优化时要考虑设备环境的整体负载情况。

### 识别和减少输入延迟

当用户与网页互动时，输入延迟是最先发生的一部分，它代表从用户触发操作到浏览器开始执行事件回调之间的等待时间。这个延迟可能因页面正在执行其他任务而变长，例如：JavaScript 的加载、解析与编译、资源提取、定时器函数执行，或密集的用户操作重叠。

![20250727110240](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250727110240.png)

特别是在网页加载初期，即页面已经开始渲染但仍未完成资源加载时，用户可能已尝试进行交互。这时，浏览器需要在主线程上完成脚本的语法解析、字节码编译和执行，容易形成长任务，阻塞主线程，延长输入延迟。

为了减少加载阶段的输入延迟，应尽量避免主线程在启动期间被沉重的脚本评估和长任务占用。保持主线程空闲、优化脚本体积和执行时机，是确保页面在加载过程中依然能快速响应用户操作的关键。

### 优化事件回调

除了优化输入延迟，事件回调的执行效率同样是 INP 的关键影响因素。理想情况下，事件处理逻辑应尽可能精简，快速完成；但若交互逻辑较复杂，建议将其拆分为更小的任务，避免形成阻塞主线程的长任务。

一种常见做法是显式让出主线程控制权，例如使用 `setTimeout()` 将部分工作推迟到新的任务队列中执行。这种“任务切片”机制能腾出主线程空隙，允许其他用户交互及时响应，从而有效改善整体交互流畅性。

虽然无差别地让出主线程控制权有助于提升响应性，但更高效的策略是在完成关键渲染任务后立即让出控制权，以便浏览器尽快绘制下一帧。这种方式可以显著减少用户感知到的交互延迟。

关键思想是：事件回调中只保留会影响界面更新的最小逻辑，其余工作推迟执行。这样既能保证用户操作后立即看到反馈，又能避免渲染被额外逻辑阻塞。

以富文本编辑器为例，用户每次输入字符时可能触发多个后续操作：

1. 更新文本框内容并应用格式（必须在下一帧前完成）

2. 更新字数统计

3. 检查拼写错误

4. 保存草稿内容

其中只有第 1 项是绘制前的必要操作，其余任务可延迟处理。可使用如下结构优化：

```js
textBox.addEventListener("input", (inputEvent) => {
  // 立即更新界面：这是用户期待看到的反馈
  updateTextBox(inputEvent);

  // 将其他非关键逻辑推迟到后续任务执行
  requestAnimationFrame(() => {
    setTimeout(() => {
      const text = textBox.textContent;
      updateWordCount(text);
      checkSpelling(text);
      saveChanges(text);
    }, 0);
  });
});
```

这种结构有效平衡了响应速度与功能处理量，显著优化 INP 指标，提升交互体验。

### 避免布局抖动

布局抖动（Layout Thrashing，也称为强制同步布局）是一种常见的渲染性能问题，发生在布局计算被频繁、同步触发时。具体来说，当 JavaScript 在同一执行任务中先修改样式再立即读取布局属性（如 `offsetHeight`、`getBoundingClientRect()` 等）时，浏览器被迫立刻重新计算布局，从而引发性能瓶颈。

这类行为会打断浏览器的渲染优化流程，导致主线程阻塞，影响滚动、动画和交互的流畅性。

![20250727111056](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250727111056.png)

在 `Chrome DevTools` 的 `Performance` 面板中，如果存在布局抖动，相关的渲染任务堆栈右上角会出现一个红色三角形警示，常见标记为 `“Recalculate Style”` 或 `“Layout”`。

布局抖动会导致性能下降，因为当 JavaScript 在同一个任务中先修改样式，又立即读取布局信息（如尺寸或位置），浏览器不得不同步执行样式计算和布局。这种同步处理会阻塞主线程，原本可以异步执行的渲染工作被强行提前执行，严重影响页面响应和渲染效率。

### 最大限度缩短呈现延迟时间

互动标记的呈现延迟是指从互动事件回调运行完毕到浏览器能够绘制显示最终视觉更改的下一个帧之间的时间。

#### 尽量减小 DOM 大小以优化渲染性能

较小的 DOM 通常意味着更快的渲染效率。随着 DOM 体积变大，浏览器在解析、样式计算和布局阶段的工作量会显著增加，特别是在以下两种场景下尤为明显：

- 初始渲染时：大型 DOM 会增加页面加载和首屏渲染所需的计算量；

- 用户交互后：每次 DOM 变动都可能触发大量重排和重绘，延迟下一帧的呈现。

虽然 DOM 大小与性能的关系并非完全线性，但结构复杂、嵌套层级过深的 DOM 无疑会成为性能瓶颈。

你可以通过以下方式控制 DOM 规模：

- 扁平化嵌套结构，避免深层次节点；

- 推迟加载非关键内容，交互后再动态插入；

- 清理无效或重复的 DOM 元素。

需要注意的是，有些应用场景中 DOM 的复杂性是难以避免的。此时可结合虚拟滚动、懒加载等技术，尽可能减少实际渲染的节点数量。

#### 使用 `content-visibility` 来延迟渲染屏幕外元素 —— 降低渲染负载，优化 INP 表现

`content-visibility` 是一项 CSS 属性，用来 告诉浏览器可以跳过渲染当前不在视口中的元素，从而减少样式计算、布局和绘制的成本。

它的主要作用是：

- 延迟渲染：屏幕外的元素不会立即进行渲染，直到用户滚动至其附近才触发；

- 加速首屏加载：减轻初始渲染压力，提高 FCP 和 INP；

- 提升滚动和交互性能：让页面在滚动或触发交互时更流畅、更及时响应。

这对于内容较长、组件较多的页面（如文章、商品列表、评论区等）尤其有效。配合 `content-visibility: auto` 和 `contain-intrinsic-size`，可以做到懒渲染 + 防抖动，在不牺牲可用性的前提下，大幅降低主线程负载。

它的主要作用有以下这桑方面：

- 延迟加载复杂 DOM 区块（如图文列表、折叠面板）

- 优化长列表滚动性能

- 提高互动阶段（如点击、输入）响应速度

如下代码所示：

```css
.card {
  content-visibility: auto;
  contain-intrinsic-size: 300px; /* 占位高度，避免闪动 */
}
```

### 注意使用 JavaScript 渲染 HTML 存在性能开销

浏览器渲染 HTML 的过程涉及 DOM 解析、样式应用、布局计算和绘制，这些都是必要的性能成本。但不同的渲染方式，其性能影响差异巨大。

当 HTML 由服务器发送时，浏览器会以流式方式逐块解析和渲染页面内容。这种方式天然具备让出主线程的机制，能边接收边解析，最大化加载效率。

相比之下，使用 JavaScript 在客户端生成 HTML（如常见的单页应用 SPA）则开销更大：
不仅需要先执行 JS 脚本来构建 DOM，还会导致主线程长时间占用，直到整个 HTML 渲染完成才会释放，这会延迟下一帧的呈现，造成响应迟钝。

**即使不是 SPA 页面，用户交互中通过 JS 动态生成大量 HTML 也会带来类似问题。因此应注意以下几点：**

- 避免在主线程一次性渲染大量 HTML；

- 使用渐进式渲染或分批插入（如 `requestIdleCallback`）；

- 优先服务器渲染首屏内容，再用 JS 补充交互逻辑；

- 如果使用虚拟 DOM 框架，控制更新范围，避免全量重绘。

- 批量 DOM 更新使用 DocumentFragment 等中间结构。

通过合理控制 JavaScript 渲染策略，可大幅优化交互性能，降低 INP 和 TBT 风险。

## 总结

INP（Interaction to Next Paint）是衡量网页交互响应性能的核心指标，关注用户操作后页面多久给出视觉反馈。它统计用户访问期间所有点击、点按和键盘操作的响应延迟，并选取其中表现最差但不异常的一次作为最终值。

相比仅测量首次交互的 FID，INP 更全面地反映了页面在整个生命周期内的真实响应体验。较低的 INP 值表示网页能快速反馈用户输入，提升交互流畅度。优化 INP 的关键在于缩短输入延迟、事件处理和首帧渲染时间。
