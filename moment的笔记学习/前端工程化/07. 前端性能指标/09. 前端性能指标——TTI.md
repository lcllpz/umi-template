TTI（可交互时间）是一种实验室性能指标，用于衡量网页从开始加载到能够稳定响应用户交互所需的时间。它帮助识别这样的问题，页面看似加载完成，但实际上仍无法响应点击、输入等操作。

## 什么是 TTI？

TTI 指标用于衡量**从网页开始加载到主要子资源加载完成**，且能够快速可靠地响应用户输入的时间。

如需根据网页的性能轨迹计算 TTI，请按以下步骤操作：

1. `First Contentful Paint (FCP)` 开始。

2. 向前搜索时间，以找到至少 5 秒的空闲时间窗口，其中空闲时间窗口定义为：没有长任务，并且正在进行的网络 GET 请求不超过 2 个。

3. 向后搜索安静时段之前的最后一个长任务，如果找不到长任务，则在 FCP 处停止。

4. `TTI` 是安静期之前的最后一个长任务的结束时间（如果未找到长任务，则与 FCP 相同）。

如下图所示：

![20250725225719](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250725225719.png)

过去，开发者会优化网页以缩短呈现时间，有时会以牺牲 TTI 为代价。

要达到 TTI（可交互时间），必须首先达到 FCP（首次内容绘制），因为 FCP 标志着页面开始显示可见内容的时间点。如果 TTI 与 FCP 相差太远，意味着用户看到内容了，但却无法立即交互。

![20250725230056](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250725230056.png)

这种“表面可用、实际不可用”的状态会让用户看到内容却无法操作，导致点击无响应、页面卡顿，从而产生明显的性能不佳体验。

使用服务器端渲染（SSR）等技术时，页面可能看起来已可交互（如按钮、链接已渲染），但实际上仍不可操作，因为主线程被阻塞，或控制这些元素的 JavaScript 代码尚未加载。

对于这种情况，用户可能的反应：

- 较轻的情况：用户感到页面反应迟钝，体验不佳

- 严重的情况：用户误以为页面已损坏，选择离开，甚至对品牌产生不信任感

为避免“假可交互”带来的负面体验：

1. 尽量缩小 FCP 与 TTI 之间的时间差

2. 如果存在明显延迟，应通过视觉提示明确告知用户该页面组件尚不可操作（如加载动画、按钮禁用状态等）

## 如何计算 TTI

在 Lighthouse 中，TTI（可交互时间）是通过识别最后一个长任务的结束时间来测量的。这个“最后的长任务”需满足以下条件：

1. 页面已经触发了 FCP（首次内容绘制）；

2. 在此之后，存在一个至少持续 5 秒的“空闲窗口”，且不被任何 CPU 或网络活动中断；

3. 这个“空闲窗口”必须同时满足：
   - CPU 空闲：主线程上没有任何超过 50ms 的长任务；

   - 网络空闲：活跃的网络请求数量不超过两个。

在上述前提下，TTI 被定义为这个“空闲窗口”开始前，最后一个长任务的结束时间。如果在 FCP 与空闲窗口之间不存在长任务，则 TTI 直接等于 FCP。

这表明页面不仅已经呈现内容，而且浏览器已完成关键脚本的执行与资源的加载，用户此时可以可靠地与页面交互。

但如果在检测过程中，CPU 或网络空闲状态被打断（例如执行新的 JS 脚本或发起新的资源请求），Lighthouse 会延后 TTI，直到找到下一个满足 5 秒连续空闲条件的窗口。换句话说，任何新的长任务或网络活动，都会推迟页面被判定为“可交互”的时刻。

如下图所示：

![20250725231348](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250725231348.png)

在这张图中，虽然 `A.js` 和 `C.js` 都是超过 `50ms` 的长任务，但只有 `C.js` 被用于计算 `TTI`。因为 `TTI` 的判定依赖于：`FCP` 之后，找到一个连续 `5` 秒 `CPU` 和网络都空闲的窗口。

`A.js` 虽早已结束，但其后仍有脚本执行（如` C.js`）以及新的网络请求不断发起，页面处于持续活跃中。

而在 `C.js` 结束后，网络请求下降到 `2` 个以内，主线程也没有新的长任务，才首次满足“空闲窗口”条件。因此，`TTI` 被定在 `C.js` 结束的时间点。

## 如何计算 TTI 得分

Lighthouse 会根据 [HTTP 归档（HTTP Archive）](https://httparchive.org/) 中的真实网站数据，将你网页的 TTI 与其他网站进行比较并计算得分。

例如，如果第 99 百分位的网站在 2.2 秒内达到 TTI，而你的网站 TTI 也是 2.2 秒，那你将获得约 99 分的得分。

TTI 得分分级标准（以秒为单位），如下表所示：

| TTI 值范围   | 颜色标记 | 性能评级 |
| ------------ | -------- | -------- |
| 0 – 3.8 秒   | 🟢 绿色  | 快速     |
| 3.9 – 7.3 秒 | 🟠 橙色  | 中度     |
| 超过 7.3 秒  | 🔴 红色  | 缓慢     |

越低的 `TTI` 意味着页面越快达到可交互状态，从而获得更高的 `Lighthouse` 得分。为了获得绿色等级，建议将 `TTI` 优化到 `3.8` 秒以内。

## 什么原因导致 TTI 变慢？

### 巨大的网络负载大小

FCP（首次内容绘制） 是指页面上首次显示“有意义”元素的时间点。无论该元素的类型如何，如果它上方存在阻塞渲染的资源（如较大的 `<script>` 或 `<link>` 标签），这些资源在网络较差的环境下加载缓慢，都会导致首屏内容的显示被延迟。

为避免这种情况，建议优化代码结构，使其更轻量。具体包括：尽可能压缩和减小资源体积，减少对大型第三方库的依赖，以提升加载速度并加快 FCP 的触发时间。

### 页面加载时包含过多的 JavaScript

如果页面加载时包含过多的 `JavaScript`，就会显著拖慢性能，尤其影响 `FCP` 和 `LCP` 的时间。

针对这一点，我们反复强调的优化原则就是：按需加载（`Lazy/On-demand Loading`）。可以理解为“吃多少，拿多少”——只加载当前视口所需的 JS，不要一次性加载整站资源。否则就像胡吃海喝，不仅对性能“消化不良”，也会让用户体验变差。

通过合理拆分模块、延迟加载非关键 JS，可以让页面更轻盈，首屏加载更快，交互也更及时。

### 同时进行多个网络请求

最后但同样重要的一点是：网络请求数量也是影响页面性能的重要因素。

图片本身不会阻塞渲染——当浏览器解析 HTML 遇到 `<img>` 标签时，会立即开始加载图片，同时继续处理其他内容，而不会等待图片加载完成。这听起来似乎没问题，但如果页面中存在大量未优化图片，浏览器将同时发起大量请求，维持多个连接，从而拖慢资源加载，间接延迟页面达到可交互状态（TTI）。

结合这一点，我们可以得出一个普遍结论：

> ❝TTI 缓慢的主要原因，是现代网站普遍依赖大量 JavaScript 所致。❞

特别是长时间 JavaScript 执行任务（即耗时超过 50ms 的任务），会严重占用浏览器主线程，阻止其及时响应用户操作。

由于浏览器依赖主线程完成解析、布局、绑定事件等关键操作，一旦主线程长时间被 JS 占用，页面即使看起来已加载，也仍无法响应交互，TTI 就会被延后。

## 优化 TTI

要提高页面的 TTI 表现，使网页更快可用、响应更流畅，需要从 资源加载、主线程执行和网络效率 三个维度入手。以下是通用且实用的优化建议：

### 一、优化 JavaScript 加载与执行

- 压缩并裁剪 JavaScript：移除未使用的代码，减少不必要的脚本传输；

- 拆分代码并按需加载：避免将所有 JS 打包发送，仅加载用户当前视图所需部分；

- 缩短 JS 执行时间：将长任务拆分为多个小任务，减少阻塞时间；

- 延迟加载第三方脚本：如社交分享、广告、播放器等非核心功能脚本，延后加载；

- 使用 `defer` 或 `async` 属性：避免脚本阻塞 HTML 解析，提高页面可用性；

- 尽量减少主线程压力：将非必要计算任务转移到 Web Worker 或后台异步处理。

### 二、优化网络连接与资源调度

- 预连接关键源：使用 `<link rel="preconnect">` 提前建立与重要域名的 TCP/TLS 连接；

- 预加载关键请求：对字体、首屏图像、JS 模块使用 `<link rel="preload">` 提前加载；

- 最大程度压缩请求链路深度：减少重定向、依赖级联的加载路径；

- 使用 CDN 靠近用户：静态资源应分发至距离用户最近的节点，加快响应；

- 避免冗余 HTTP 请求：合并小资源，精简字体文件，防止因字体或图片碎片化而引起的加载延迟；

- 保持请求数量与传输体积最小化：控制并发数量与文件体积，减轻加载压力。

TTI 优化的核心在于尽早渲染关键内容、尽量减少阻塞用户交互的因素，这不仅是技术层面的提升，更体现了以用户体验为导向的前端开发理念。

## 总结

TTI（Time to Interactive，可交互时间）是衡量网页从开始加载到能够稳定响应用户操作所需的时间。它反映了用户何时可以真正使用页面，而不仅仅是看到内容。

TTI 受 JavaScript 执行、资源加载、主线程繁忙等因素影响，过长的 TTI 会导致用户感知“页面卡顿”或“假加载”。优化 TTI 需要控制脚本体积、拆分非关键任务、懒加载图片和第三方脚本，并减少主线程阻塞。

良好的 TTI 表现能显著提升页面的可用性与用户体验。
