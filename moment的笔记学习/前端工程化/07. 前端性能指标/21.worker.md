# Web Worker

**Dedicated Worker（`new Worker()`）**：只能服务于创建它的页面上下文；**页面关闭后通常随之终止**，不会作为「整站后台服务」常驻。

> **补充**：`SharedWorker` 可被同源多页面共享，但使用与兼容度相对冷门；日常说「Web Worker」多指 Dedicated。

Web Worker 的意义：把 **CPU 密集、耗时** 的任务从主线程剥离，让主线程更专注渲染与交互（主线程被长任务阻塞时使用），例如：

- 懒加载相关计算
- 文本分析、流式数据处理
- Canvas 绘制、图像处理

**注意点**：

- **同源**：Worker 脚本须与页面脚本同源。
- **DOM 限制**：Worker 全局与主线程不同，**不能直接读/写页面 DOM**；不能使用 `document`、`window` 等（可用 `self`、部分 API 如 `navigator` 等，视环境而定）。
- **通信**：主线程与 Worker **通过 `postMessage` / `onmessage` 传数据**（结构化克隆，非共享内存，除非另配合 `SharedArrayBuffer` 等）。
- **脚本限制**：Worker 内不能使用 `alert`、`confirm` 等阻塞 UI 的 API；可用 `fetch` / `XMLHttpRequest` 发网络请求。
- **文件协议**：不能依赖 `file://` 随意读本地文件系统；脚本一般来自网络或打包产物。

```js
const worker = new Worker("sum.worker.js");
worker.postMessage({ iterations: ITERATIONS });

// sum.worker.js
self.onmessage = function (e) {
  const iterations = e.data?.iterations ?? 80_000_000;
  const start = performance.now();
  let sum = 0;
  for (let i = 0; i < iterations; i++) {
    sum += i;
  }
  const ms = performance.now() - start;
  self.postMessage({
    sum,
    iterations,
    ms,
    thread: "worker",
  });
};
```

# Service Worker

在规范关系上：**Service Worker 是 Web Worker 的一种**（W3C：`A service worker is a type of web worker`），但能力与生命周期与 Dedicated Worker **差异很大**。

可理解为：**位于 Web 应用、浏览器与网络之间的可编程代理**（MDN），典型能力包括：

- **拦截** `fetch` 请求并自定义响应（离线、缓存、回退）
- 与页面通过 `postMessage` 通信
- 为 **Web Push**、部分后台能力提供事件入口
- **HTTPS** 生产环境要求（`localhost` 等例外）

## 生命周期

整体顺序可记：**注册 → 下载脚本 → 安装 →（可能等待）→ 激活 → 运行中处理事件**；更新时新版本常与旧版 **并存一段时间**（`waiting`），直到旧 client 释放或调用 `skipWaiting()`。

创建 / 注册 Service Worker 之后，**并不是所有浏览器窗口都会被接管；只有同源、且在注册 scope 内的页面（以及之后打开的符合条件的页面）才会由该 SW 服务接管**；其它网站、其它路径的窗口完全不受影响。

### 1. 注册（页面主线程）

- **注意**：**首次**需页面在线拉取脚本；`scope` 不能超出脚本所在目录规则（常见把 `sw.js` 放根路径）。
  脚本在子目录里，默认只能「向下」管自己这一支子树，不能偷偷扩大到父级目录。例如：若把 sw.js 放在 /static/sw.js，默认只能管 /static/...，管不到首页 / 和别的业务路径。把 sw.js 放在 https://域名/sw.js（站点根路径），默认 scope 就是 /，整站都在控制范围内。

> 若必须把文件放在子目录（例如 CDN 路径 /assets/sw.js），又想让 scope 是 /，服务器对 sw.js 这个请求的响应可以加头：Service-Worker-Allowed: /
> 表示浏览器允许这次注册的 scope 扩大到 头里写的路径（常见就是 /）。没有这条头，就仍然受「不能超出脚本目录」限制。

```js
// 1. 特性检测：判断浏览器是否支持 Service Worker
if ("serviceWorker" in navigator) {
  // 2. 推荐在 window.onload 中注册，避免占用首屏网络资源
  window.addEventListener("load", async () => {
    try {
      // 3. 注册 sw.js，注意路径和作用域（Scope）
      const registration = await navigator.serviceWorker.register("/sw.js");
      console.log("Service Worker 注册成功, 作用域为:", registration.scope);

      // 可选：监听 SW 更新（当有新版本 sw.js 安装时）
      // 在浏览器发现「有一个新版本 Service Worker 正在安装」时触发。
      registration.addEventListener("updatefound", () => {
        console.log("发现新的 Service Worker 版本！");
      });
    } catch (err) {
      console.error("Service Worker 注册失败:", err);
    }
  });
} else {
  console.warn("当前浏览器不支持 Service Worker");
}
```

### 2. 下载（浏览器检查更新）

浏览器对比已安装脚本与网络 **`sw.js` 是否变化**（字节级）；变化则拉新版本。

- **注意**：仅 CDN 上静态资源更新、**`sw.js` 一字未变**，不一定会触发新一轮 `install`。

### 3. `install`

第一次安装或更新时进入

```js
/**
 * 生命周期 1：Install (安装阶段)
 * 触发时机：第一次注册 SW，或者 sw.js 文件发生了字节上的变化时。
 * 作用：执行“预缓存”操作，把静态资源下载到浏览器的 Cache Storage 中。
 */
self.addEventListener("install", (event) => {
  console.log("[SW] 正在安装...");

  // event.waitUntil 确保缓存完成后才进入下一个阶段
  event.waitUntil(
    caches
      .open(CACHE_NAME)
      .then((cache) => {
        console.log("[SW] 正在预缓存静态资源");
        return cache.addAll(PRECACHE_URLS);
      })
      .then(() => {
        // 强制当前 SW 立即进入 activate 阶段，跳过等待
        return self.skipWaiting();
      }),
  );
});
```

### 3. `activate`

如果注册和安装成功，服务工件会激活，其状态变为 'activating', SW 开始接管

- **`event.waitUntil`**：内做 **删旧版本 `Cache`**、迁移数据结构、清理过期条目。
- **`clients.claim()`**：让当前已打开的、在 `scope` 下的页面 **立即**被本 SW 控制（否则可能要下一次导航才接管）。
- **典型价值**：**发版换缓存桶名**后，在 activate **砍掉旧桶**，避免无限堆积与错配旧资源。

```js
/**
 * 生命周期 2：Activate (激活阶段)
 * 触发时机：SW 安装成功并接管页面时。
 * 作用：清理旧版本的缓存（Cache Invalidation），释放磁盘空间。
 */
self.addEventListener("activate", (event) => {
  console.log("[SW] 正在激活...");

  event.waitUntil(
    caches
      .keys()
      .then((cacheNames) => {
        return Promise.all(
          cacheNames.map((cacheName) => {
            // 如果遍历到的缓存名称与当前的 CACHE_NAME 不一致，说明是旧版本，删除它
            if (cacheName !== CACHE_NAME) {
              console.log(`[SW] 清理旧缓存: ${cacheName}`);
              return caches.delete(cacheName);
            }
          }),
        );
      })
      .then(() => {
        // 让处于 active 状态的 worker 立即控制所有打开的页面
        return self.clients.claim();
      }),
  );
});
```

### 4. 激活后（`activated` / 运行期）

创建api使用：官网链接->https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerGlobalScope/sync_event

- **`fetch`**：拦截请求；示例为「**网络优先，失败再读缓存**」，命中网络且 `ok` 时顺带 `put` 更新缓存（与后文「网络优先，回退缓存」表一致）。
  （注意：`CACHE_NAME` 为前文预缓存桶名，运行时动态缓存建议单独桶名）。

```js
// 与预缓存分开，避免和 install 里 addAll 的桶搅在一起
const RUNTIME_CACHE = `${CACHE_NAME}-runtime`;

self.addEventListener("fetch", (event) => {
  const { request } = event;
  if (request.method !== "GET") return;

  event.respondWith(
    fetch(request)
      .then((response) => {
        if (response.ok) {
          const copy = response.clone();
          caches.open(RUNTIME_CACHE).then((cache) => cache.put(request, copy));
        }
        return response;
      })
      .catch(() => caches.match(request)),
  );
});
```

- **`message`**：双方都用 `postMessage` + 对方侧的 `message` 事件，数据经**结构化克隆**传递。

| 方向      | 谁发   | 谁收                                        | 典型写法                                                                                                                                                                                         |
| --------- | ------ | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 页面 → SW | 主线程 | SW 里 `self.addEventListener("message", …)` | `navigator.serviceWorker.controller.postMessage(...)`（发给**当前控制本页**的 SW）；或 `registration.waiting.postMessage(...)`（发给**还在 waiting、尚未接管**的新 SW，用于 `skipWaiting` 场景） |
| SW → 页面 | SW     | 主线程                                      | SW 里对**发来消息的那一个页面** `event.source.postMessage(...)`；或对**多个标签**用 `clients.matchAll()` 再逐个 `client.postMessage(...)` 广播                                                   |

下面拆成两个文件，避免和「一段里混写」混淆。

**① Service Worker 文件（`sw.js`，在 SW 线程执行）**

```js
self.addEventListener("message", (event) => {
  // event.source：发消息的 Client（通常是 WindowClient），可用来单播回该页
  if (event.data?.type === "SKIP_WAITING") {
    self.skipWaiting();
    return;
  }
  if (event.data?.type === "PING") {
    event.source?.postMessage({ type: "PONG", from: "sw" });
  }
});
```

**② 页面脚本**
在主线程执行；`navigator.serviceWorker.controller` 仅在「本页已被 SW 控制」后才有值，否则为 `null`，常需刷新或依赖上文 `activate` 里的 `clients.claim()`

```js
// 发给「waiting」里的新版本 SW（与 updatefound / waiting 配合做「点刷新再接管」）
function skipWaitingViaMessage(registration) {
  if (registration.waiting) {
    registration.waiting.postMessage({ type: "SKIP_WAITING" });
  }
}

// 发给「当前正在控制本页」的 SW → 触发 sw.js 里对 PING 的分支 → 再通过 event.source 回 PONG
navigator.serviceWorker.controller?.postMessage({ type: "PING" });

// 主线程监听：收到的是 SW 里 postMessage 过来的消息（例如上面的 PONG）
navigator.serviceWorker.addEventListener("message", (e) => {
  console.log("页面收到 SW:", e.data);
});
```

- **`push` / `notificationclick`**：推送载荷在 SW 内处理；点击系统通知可 `focus` 已有标签或 `openWindow`。**真实 Web Push** 还需 `pushManager.subscribe`、VAPID、服务端按协议推送；此处仅事件形态。
  ![alt text](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images202507301652251.png)

```js
self.addEventListener("push", (event) => {
  const body = event.data ? event.data.text() : "无正文";
  event.waitUntil(
    self.registration.showNotification("站点推送", {
      body,
      data: { url: "/" },
    }),
  );
});

self.addEventListener("notificationclick", (event) => {
  event.notification.close();
  const url = event.notification.data?.url || "/";
  event.waitUntil(
    self.clients
      .matchAll({ type: "window", includeUncontrolled: true })
      .then((clientList) => {
        const existing = clientList.find((c) =>
          c.url.includes(self.location.origin),
        );
        if (existing) return existing.focus();
        return self.clients.openWindow(url);
      }),
  );
});
```

self.addEventListener("sync", (event) => {

    event.waitUntil(

## fetch缓存策略一览（

> 参考：[Chrome for Developers — Service Worker 缓存策略](https://developer.chrome.google.cn/docs/workbox/caching-strategies-overview#caching_strategies)

| 策略                                     | 流程要点                                                                 | 典型用途                                          | 注意                                                                      |
| ---------------------------------------- | ------------------------------------------------------------------------ | ------------------------------------------------- | ------------------------------------------------------------------------- |
| **仅缓存（Cache only）**                 | 只 `cache.match`，**不发起网络**；未命中则无响应或需另行兜底             | **预缓存**的壳、固定版本静态；离线必出            | 未预缓存的资源会挂；**SW 更新前**缓存内容不会按此模式自动更新             |
| **仅网络（Network only）**               | **不调** `respondWith`（或显式放行），走默认网络                         | 强实时、必须最新（接口、支付页等）                | **离线必失败**                                                            |
| **缓存优先，回退网络（Cache first）**    | 先 `match`，命中即返回；**未命中**再 `fetch`，成功则 **`put`** 再返回    | **带 hash 的** JS/CSS/图/字体；离线友好、二访加速 | **固定 URL 无 hash** 易长期旧资源，慎 cache-only                          |
| **网络优先，回退缓存（Network first）**  | **先 `fetch`**，成功可 **`put`** 更新缓存并返回；**失败**再 `match` 缓存 | **HTML、API**：在线要新，离线/失败要「上次可用」  | 弱网会一直等网络直到失败才回退，可配 **超时转缓存**（Workbox 有插件思路） |
| **Stale while revalidate（过期再验证）** | 有缓存则 **先返回缓存**（快）；**同时**后台 `fetch`，成功则 **更新缓存** | 头像、非关键配置、可稍旧的列表                    | **当次**请求未必是最新；实现与排障比前几种复杂                            |

## service worker更新/怎么更新缓存的资源

1. 手动触发更新检查:重新走install/activate

```js
navigator.serviceWorker.ready.then((registration) => {
  registration.update();
});
```

2. 假设 Service Worker 的网址或作用域保持不变，则当前安装的 Service Worker 仅在其内容发生更改时才会更新为新版本。
   > **最佳实践**：所以我们通常通过修改文件开头的 `const CACHE_NAME = 'v1.0.1'` 来触发更新。

- 维护CACHE_VERSION名称，在install 事件中船舰新的新 Cache 实例，更改预缓存的资源名称
- activate ：清旧缓存
  > `前提是PRECACHE_URLS的资源存在更新才会获取最新的资源`

```js
// 定义缓存名称，每次更新前端资源时，只需修改这里的版本号（非常重要！）
const CACHE_NAME = "app-cache-v1.0.0";

// 需要预缓存的静态资源列表（相当于我们的前端“离线包”）
const PRECACHE_URLS = [
  "/",
  "/index.html",
  "/styles/main.css",
  "/scripts/app.js",
  "/images/logo.png",
];

/**
 * 生命周期 1：Install (安装阶段)
 * 触发时机：第一次注册 SW，或者 sw.js 文件发生了字节上的变化时。
 * 作用：执行“预缓存”操作，把静态资源下载到浏览器的 Cache Storage 中。
 */
self.addEventListener("install", (event) => {
  console.log("[SW] 正在安装...");

  // event.waitUntil 确保缓存完成后才进入下一个阶段
  event.waitUntil(
    caches
      .open(CACHE_NAME)
      .then((cache) => {
        console.log("[SW] 正在预缓存静态资源");
        return cache.addAll(PRECACHE_URLS);
      })
      .then(() => {
        // 强制当前 SW 立即进入 activate 阶段，跳过等待
        return self.skipWaiting();
      }),
  );
});

/**
 * 生命周期 2：Activate (激活阶段)
 * 触发时机：SW 安装成功并接管页面时。
 * 作用：清理旧版本的缓存（Cache Invalidation），释放磁盘空间。
 */
self.addEventListener("activate", (event) => {
  console.log("[SW] 正在激活...");

  event.waitUntil(
    caches
      .keys()
      .then((cacheNames) => {
        return Promise.all(
          cacheNames.map((cacheName) => {
            // 如果遍历到的缓存名称与当前的 CACHE_NAME 不一致，说明是旧版本，删除它
            if (cacheName !== CACHE_NAME) {
              console.log(`[SW] 清理旧缓存: ${cacheName}`);
              return caches.delete(cacheName);
            }
          }),
        );
      })
      .then(() => {
        // 让处于 active 状态的 worker 立即控制所有打开的页面
        return self.clients.claim();
      }),
  );
});

/**
 * 生命周期 3：Fetch (拦截网络请求)
 * 触发时机：页面发起的任何 HTTP 请求（HTML、JS、图片、Ajax 等）。
 * 作用：实现“离线包”的秒开体验 —— 缓存优先策略。
 */
self.addEventListener("fetch", (event) => {
  // 只拦截 GET 请求，忽略 POST、PUT 等
  if (event.request.method !== "GET") return;

  event.respondWith(
    // 1. 去 Cache Storage 中寻找是否有匹配的资源
    caches
      .match(event.request)
      .then((cachedResponse) => {
        // 【命中缓存】：直接返回本地资源，不走网络，实现“秒开”！
        if (cachedResponse) {
          console.log(`[SW] 命中缓存: ${event.request.url}`);
          return cachedResponse;
        }

        // 【未命中缓存】：降级去走真实网络请求
        console.log(`[SW] 走网络请求: ${event.request.url}`);
        return fetch(event.request).then((networkResponse) => {
          // 检查响应是否有效
          if (
            !networkResponse ||
            networkResponse.status !== 200 ||
            networkResponse.type !== "basic"
          ) {
            return networkResponse;
          }

          // 可选：实现【动态缓存】。把这次网络请求的结果存下来，下次就快了。
          // 注意：Response 是个流，只能消费一次，所以必须 clone。
          const responseToCache = networkResponse.clone();
          caches.open(CACHE_NAME).then((cache) => {
            cache.put(event.request, responseToCache);
          });

          return networkResponse;
        });
      })
      .catch(() => {
        // 兜底方案：如果断网了，且没有缓存，可以返回一个离线提示页面（Offline Page）
        // if (event.request.mode === 'navigate') {
        //   return caches.match('/offline.html');
        // }
      }),
  );
});
```

## 与 Web Worker 对比（面试常用）

一句话：**Worker 为「别挡 UI 的算力线程」；SW 为「站点的网络与后台代理」**——前者优化**帧与响应**，后者改造**加载与可达性**。

- 离线壳：在断网或极弱网时，由 Service Worker 用预缓存或缓存优先等方式，从 Cache Storage 里先返回这份壳，让页面能立刻画出界面（哪怕数据区是空的、要再提示「离线」或读 IndexedDB 里的旧数据）。

- 事件驱动：Service Worker 不是自己一直 while(true) 跑着等事做，只有浏览器派发事件时，才会去执行你注册的回调：例如fetch、message、install等
- 不保证常驻：SW 对应的执行环境可能被直接停掉（内存不够释放内存），内存里的全局变量、定时器句柄等就不在了。

- UA： 是 User Agent（用户代理） 的缩写。
  在 Web 里通常指的就是帮你访问网页的那一端程序，最常见就是浏览器（Chrome、Firefox、Safari 等）或内置 WebView。
  说「由 UA 管理」时，意思是：具体什么时候启动、挂起、关掉 Service Worker 这类行为，标准只定原则，不规定死每一毫秒，**由各个浏览器自己的实现决定**，所以写作 UA 而不是写死「Chrome 一定怎样」。

  | 维度                 | Web Worker                                                                                | Service Worker                                                                                                                                                                                                                                   |
  | -------------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
  | **核心职责**         | 把 CPU 密集、可并行的逻辑**迁出主线程**，保住交互与渲染帧                                 | 在**同源 + scope** 内做**请求拦截、缓存版本、离线壳、推送/通知**等站点级策略                                                                                                                                                                     |
  | **谁创建、和谁绑定** | 页面 `new Worker()`（或 `SharedWorker`），**持有引用**才能通信；随**创建页关闭**而结束    | `navigator.serviceWorker.register()`，与**单个标签弱绑定**；同一同源、scope的tab页签都能共享                                                                                                                                                     |
  | **生命周期直觉**     | 线程「**有人用就活着**」，不用可 `terminate` / 关页回收                                   | **事件驱动、不保证常驻**：`fetch` / `push` / `message` 等把 SW 拉起来，做完可能被 UA **随时停掉**（`setInterval` 不可靠） 或者这么理解：SW 按源注册，scope匹配，可多 client 共享逻辑，页面关闭不等于 SW 立即销毁（由 UA 管理，可被事件唤醒或终止 |
  | **对「全站网络」**   | 自己 `fetch` 只影响**自己发出的请求**，**不参与**文档/静态资源的默认加载管线              | `fetch` + `event.respondWith()` 可改变 **scope 内导航与子资源** 的默认获取方式（缓存优先、离线回退等）                                                                                                                                           |
  | **运行环境共性**     | 无 `window` / DOM，与主线程**结构化克隆**通信                                             | 同样无 DOM；注册依赖**安全上下文**（HTTPS 或 `localhost`）                                                                                                                                                                                       |
  | **面试常提 API**     | `postMessage` / `onmessage`、`importScripts`、可配合 **Transferable** / `OffscreenCanvas` | `install` / `activate`、`skipWaiting`、`clients.claim`、`fetch`、`push`、`sync`…；异步多用 **`event.waitUntil`** 延长单次事件寿命                                                                                                                |
  | **典型坑**           | 误把依赖 DOM 的逻辑放进 Worker；忘记大对象用 **Transferable** 减少拷贝                    | 把 SW 当**长驻定时器 / 重 CPU** 用；**版本更新**未处理 `waiting` + `skipWaiting` 导致用户长期卡在旧 SW                                                                                                                                           |

**易混点**：两者都能 `postMessage`，但 **SW 的「主菜」是 `fetch` 与生命周期**；Worker 的「主菜」是**算力卸载**，不要拿 SW 当长驻定时器或重计算线程用。（`SharedWorker` 介于二者之间：**多页面共享**一个逻辑，但仍**不拦截**全站 `fetch`。）

**口述模板（约 30s）**：web Worker 是页面拉起来的**算力副线程**，关页或 `terminate` 就没了；Service Worker 是浏览器按 **register + scope** 托管的**网络代理脚本**，不保证进程常驻，靠 `fetch` / `push` 等事件唤醒，用来改缓存与离线策略，和「把主线程算力挪走」是两条设计轴线。

## 使用场景

**值得上的典型场景**（有清晰目标再上，避免只为「二访加速静态图」，和 HTTP/CDN 缓存重复）：

1. **离线 / 极弱网兜底**：断网仍能出壳、上次文档或关键静态；可配合 **`install` 预缓存**（清单由构建生成）。
2. **对 HTML / 导航做策略**：例如 `index.html` 常 **no-cache**，可用 **网络优先 + 失败回缓存**、**SWR** 等减少弱网白屏（与「hash 静态资源靠 HTTP 就够」不矛盾）。
3. **Web Push / 通知点击**：多依赖 SW 内 `push`、`notificationclick`。
4. **复杂路由级缓存与发版协同**：不同路径不同策略；`activate` 中 **按版本清理旧 `Cache`**，避免旧壳新接口。

**注意「使用场景较少」**：仅官网/活动页、无离线/推送需求，且 **CDN + `Cache-Control`/`immutable`** 已理顺静态资源时，SW **非刚需**；微信等内置浏览器需 **单独评估能力**。

> **运行时缓存**：多数要 **至少成功拉取过一次** 才有得用；价值在 **回访、用过再断网、弱网兜底**。

> 对 **CDN 已配好长缓存 / `immutable` 的 hash 静态资源**，**HTTP 缓存**已能让二访很快，**SW 边际收益可能很小**。

> SW 仍可能多出价值在：**文档策略、离线明确回退、推送、与 HTTP 头解耦的可编程策略**等，而不是替 CDN 再给图片「多缓存一遍」。

## Workbox（简记）

- **Workbox**：Google 维护的 **SW 工具库**，把常见缓存策略、预缓存、路由等工程化；底层仍是 **原生 SW + Cache API**。

## PWA

- **PWA**：常见组合为 **`Web App Manifest` + HTTPS + Service Worker** 等，使站点可安装、可离线增强；**原生 App 不等于 PWA**，混合壳 WebView 与浏览器全能力也不等价。
