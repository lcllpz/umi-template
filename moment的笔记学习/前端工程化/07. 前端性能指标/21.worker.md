# Web Worker 特点

**Dedicated Worker（`new Worker()`）**：只能服务于创建它的页面上下文；**页面关闭后通常随之终止**，不会作为「整站后台服务」常驻。

> **补充**：`SharedWorker` 可被同源多页面共享，但使用与兼容度相对冷门；日常说「Web Worker」多指 Dedicated。

Web Worker 的意义：把 **CPU 密集、耗时** 的任务从主线程剥离，让主线程更专注渲染与交互（主线程被长任务阻塞时使用），例如：

- 懒加载相关计算
- 文本分析、流式数据处理
- Canvas 绘制、图像处理

**注意点**：

- **同源**：Worker 脚本须与页面脚本同源。
- **DOM 限制**：Worker 全局与主线程不同，**不能直接读/写页面 DOM**；不能使用 `document`、`window` 等（可用 `self`、部分 API 如 `navigator` 等，视环境而定）。
- **通信**：主线程与 Worker **通过 `postMessage` / `onmessage` 传数据**（结构化克隆，非共享内存，除非另配合 `SharedArrayBuffer` 等）。
- **脚本限制**：Worker 内不能使用 `alert`、`confirm` 等阻塞 UI 的 API；可用 `fetch` / `XMLHttpRequest` 发网络请求。
- **文件协议**：不能依赖 `file://` 随意读本地文件系统；脚本一般来自网络或打包产物。

# Service Worker 是什么

在规范关系上：**Service Worker 是 Web Worker 的一种**（W3C：`A service worker is a type of web worker`），但能力与生命周期与 Dedicated Worker **差异很大**。

可理解为：**位于 Web 应用、浏览器与网络之间的可编程代理**（MDN），典型能力包括：

- **拦截** `fetch` 请求并自定义响应（离线、缓存、回退）
- 与页面通过 `postMessage` 通信
- 为 **Web Push**、部分后台能力提供事件入口
- **HTTPS** 生产环境要求（`localhost` 等例外）

**与 Web Worker（Dedicated）对比（面试常用）**：

| 维度 | Dedicated Web Worker | Service Worker |
|------|------------------------|----------------|
| 主要目的 | **算力外包**，减轻主线程阻塞 | **请求/缓存策略**、离线、推送等站点级能力 |
| 与页面关系 | 多由单页创建，**随页生命周期** | **按源 + scope 注册**，可脱离单个标签存在（由事件唤醒，UA 可频繁终止） |
| 网络角色 | 普通发请求，**不拦截全站默认加载管线** | 可监听 **`fetch`**，用 **`respondWith`** 改变默认网络行为 |
| 典型 API | `postMessage` | `install` / `activate` / `fetch` / `push`…，强异步 |

**线程还是进程？**  
规范只定义 **独立 JS 执行环境**，不承诺「一定是线程/进程」。主流实现多为 **渲染进程内的并发线程/任务模型**；**不是**「每个 SW 一个操作系统进程」这种简单对应。

**其它相近概念**：

- **Shared Worker**：同源多页面共享（支持面相对窄）。
- **Worklet**（如 `AudioWorklet`、CSS Paint/Layout）：**不是**同一套 `Worker` API，生命周期与用途不同。

# Service Worker 到底用在哪些场景

**值得上的典型场景**（有清晰目标再上，避免只为「二访加速静态图」叠一层，和 HTTP/CDN 缓存重复）：

1. **离线 / 极弱网兜底**：断网仍能出壳、上次文档或关键静态；可配合 **`install` 预缓存**（清单由构建生成）。
2. **对 HTML / 导航做策略**：例如 `index.html` 常 **no-cache**，可用 **网络优先 + 失败回缓存**、**SWR** 等减少弱网白屏（与「hash 静态资源靠 HTTP 就够」不矛盾）。
3. **Web Push / 通知点击**：多依赖 SW 内 `push`、`notificationclick`。
4. **复杂路由级缓存与发版协同**：不同路径不同策略；`activate` 中 **按版本清理旧 `Cache`**，避免旧壳新接口。

**常见「不必上」**：仅官网/活动页、无离线/推送需求，且 **CDN + `Cache-Control`/`immutable`** 已理顺静态资源时，SW **非刚需**；微信等内置浏览器需 **单独评估能力**。

# PWA 与 Workbox（简记）

- **PWA**：常见组合为 **`Web App Manifest` + HTTPS + Service Worker** 等，使站点可安装、可离线增强；**原生 App 不等于 PWA**，混合壳 WebView 与浏览器全能力也不等价。
- **Workbox**：Google 维护的 **SW 工具库**，把常见缓存策略、预缓存、路由等工程化；底层仍是 **原生 SW + Cache API**。

# 缓存：`Cache` API 与 HTTP 缓存

- **`Cache` / `caches` 与 HTTP 缓存是两套机制**（Chrome Workbox 文档）：`Cache-Control` 等 **不自动决定** SW 里 `put` 的内容如何失效。
- **策略本质**：`fetch` 事件里 **`event.respondWith`** 决定返回 **网络 `Response` 还是 `cache.match` 的结果**，以及是否 **`cache.put` 更新**。
- **识别请求**：常用 `event.request.url`、`method`、`mode`（如 `navigate` 区分文档导航）、`destination`（资源类型）等做分支策略。

---

## 常见缓存策略一览（与 Workbox 命名对齐）

> 参考：[Chrome for Developers — Service Worker 缓存策略](https://developer.chrome.google.cn/docs/workbox/caching-strategies-overview#caching_strategies)

| 策略 | 流程要点 | 典型用途 | 注意 |
|------|----------|----------|------|
| **仅缓存（Cache only）** | 只 `cache.match`，**不发起网络**；未命中则无响应或需另行兜底 | **预缓存**的壳、固定版本静态；离线必出 | 未预缓存的资源会挂；**SW 更新前**缓存内容不会按此模式自动更新 |
| **仅网络（Network only）** | **不调** `respondWith`（或显式放行），走默认网络 | 强实时、必须最新（接口、支付页等） | **离线必失败** |
| **缓存优先，回退网络（Cache first）** | 先 `match`，命中即返回；**未命中**再 `fetch`，成功则 **`put`** 再返回 | **带 hash 的** JS/CSS/图/字体；离线友好、二访加速 | **固定 URL 无 hash** 易长期旧资源，慎 cache-only |
| **网络优先，回退缓存（Network first）** | **先 `fetch`**，成功可 **`put`** 更新缓存并返回；**失败**再 `match` 缓存 | **HTML、API**：在线要新，离线/失败要「上次可用」 | 弱网会一直等网络直到失败才回退，可配 **超时转缓存**（Workbox 有插件思路） |
| **Stale while revalidate（过期再验证）** | 有缓存则 **先返回缓存**（快）；**同时**后台 `fetch`，成功则 **更新缓存** | 头像、非关键配置、可稍旧的列表 | **当次**请求未必是最新；实现与排障比前几种复杂 |

**组合思路**：文档/接口与静态资源 **拆策略**；静态 **hash + cache first**，导航 **network first + 缓存兜底**，头像类 **SWR**。

# Service Worker 生命周期与各阶段能做什么

整体顺序可记：**注册 → 下载脚本 → 安装 →（可能等待）→ 激活 → 运行中处理事件**；更新时新版本常与旧版 **并存一段时间**（`waiting`），直到旧 client 释放或调用 `skipWaiting()`。

## 1. 注册（页面主线程，`navigator.serviceWorker.register`）

- **能做什么**：指定 `sw.js` URL 与 **`scope`**（控制路径范围）；拿到 `registration` 监听 `updatefound` 等。
- **注意**：**首次**需页面在线拉取脚本；`scope` 不能超出脚本所在目录规则（常见把 `sw.js` 放根路径）。

## 2. 下载（浏览器检查更新）

- **能做什么**：浏览器对比已安装脚本与网络 **`sw.js` 是否变化**（字节级）；变化则拉新版本。
- **注意**：仅 CDN 上静态资源更新、**`sw.js` 一字未变**，不一定会触发新一轮 `install`（与「发版与 `CACHE_VERSION`」一节呼应）。

## 3. `install`（新 SW 第一次安装或更新时进入）

- **能做什么**：
  - **`event.waitUntil(Promise)`**：延长安装阶段，等 **预缓存**（`caches.open` + `addAll` / `put`）完成再视为安装成功/失败。
  - 调用 **`self.skipWaiting()`**：跳过 waiting，**尽快**让新 SW 在下次有机会变 active（是否调用需结合「是否允许用户仍短暂跑旧逻辑」评估）。
- **不能默认指望**：`fetch` 监听器在 **尚未 `activate` 完成前** 可能对部分请求 **还未接管**（文档会写要等激活；复杂场景用 `clients.claim` 配合）。

## 4. `waiting`（已安装未激活）

- **含义**：旧 SW 仍控制已有页面时，新 SW **装好了但处于 waiting**。
- **能做什么**：页面可提示用户刷新；新 SW 内可继续等待直到旧 client 关闭，或已在 `install` 里 `skipWaiting()` 缩短等待。

## 5. `activate`（新 SW 开始接管）

- **能做什么**：
  - **`event.waitUntil`**：内做 **删旧版本 `Cache`**、迁移数据结构、清理过期条目。
  - **`clients.claim()`**：让当前已打开的、在 `scope` 下的页面 **立即**被本 SW 控制（否则可能要下一次导航才接管）。
- **典型价值**：**发版换缓存桶名**后，在 activate **砍掉旧桶**，避免无限堆积与错配旧资源。

## 6. 激活后（`activated` / 运行期）

- **能做什么**：
  - **`fetch`**：拦截请求，实现上表各类缓存策略。
  - **`message`**：与页面双向通信。
  - **`push` / `notificationclick`**：推送与通知。
  - **`sync`**（Background Sync，支持度视浏览器）：后台重试等。
- **注意**：SW **可被 UA 随时杀掉**；逻辑应 **幂等、可重入**，不要假设「常驻进程」。

## 7. `redundant`（被淘汰）

- **含义**：新版本取代或注册被卸载，旧 SW 进入 **废弃**。
- **能做什么**：无；仅表示旧上下文结束。

# 发版与 `CACHE_VERSION`（自维护桶名）

- **SW 生命周期是否再走 `install/activate`**：主要看 **`sw.js` 是否变更**（字节级）；你在文件里改 **`CACHE_VERSION` 常量**也会改变 `sw.js`，从而触发更新。
- **`CACHE_VERSION` 的作用**（若用作 `caches.open` 名字 + `activate` 删旧桶）：**换桶、清旧缓存**；**不能替代**「入口 HTML / 预缓存清单已指向本次构建的新 URL（如新 hash）」。
- **仅发新静态、但 `sw.js` 完全不变**：不一定会跑新一轮 `install`；依赖 **预缓存 `addAll`** 的部分不会自动刷新，故构建常 **注入版本或清单 hash** 保证 `sw.js` 变化。

**带 hash 的静态资源文件名**：可用正则粗判「路径里有一段 hash + `.js`/`.css`」，便于对 **immutable 资源** 使用 **缓存优先**；正则需与团队实际文件名规则一致。

---

# 离线能力是不是「没意义」（必须先下过）

- **运行时缓存**：多数要 **至少成功拉取过一次** 才有得用；价值在 **回访、用过再断网、弱网兜底**。
- **`install` 预缓存**：按构建清单在装 SW 时拉资源，**不要求用户事先访问每个 URL**；但仍需 **至少一次在线** 完成 SW 安装（无法「从未联网凭空变文件」）。

---

# 与「仅 HTTP 缓存二访」的关系

- 对 **CDN 已配好长缓存 / `immutable` 的 hash 静态资源**，**HTTP 缓存**已能让二访很快，**SW 边际收益可能很小**。
- SW 仍可能多出价值在：**文档策略、离线明确回退、推送、与 HTTP 头解耦的可编程策略**等，而不是替 CDN 再给图片「多缓存一遍」。

---

# WebView 白屏（简记）

**缓解优先顺序**：原生 **占位/Splash/背景色/预热 WebView/离线包** + H5 **首屏 HTML 与壳、拆包减主线程**；**不要默认指望 SW**（WebView 对 SW 支持可能受限，且常与壳内离线包方案二选一或需统一）。

---

# JSON 能否进 SW 缓存

- **可以**：缓存的是 **`Response`**，与 JSON/HTML 类型无关；**`GET`** 最常见。
- **慎用**：带 **鉴权/个性化** 的接口要避免串数据、过期态；强实时接口优先 **Network first** 或不做长期 cache-only。

---

# ServiceWorker 与 Webworker 的不同（原文档要点合并）

- **生命周期与范围**：Dedicated 多随页面；SW **按源注册**，可多 client 共享逻辑，**页面关闭不等于 SW 立即销毁**（由 UA 管理，可被事件唤醒或终止）。
- **能力**：SW 核心是 **`fetch` 拦截与缓存**；Dedicated 核心是 **并行计算**。
- **环境**：SW 需 **HTTPS**（及例外环境）；Dedicated 随页面同源策略。
