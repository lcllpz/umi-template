在提升 JavaScript 应用性能时，常见的建议包括：

- 避免阻塞主线程

- 拆分长任务

这些确实是很重要的原则，但实际应用中究竟需要做哪些工作？比如：减少 JavaScript 代码量是否一定能让界面响应更快？ 有时候可以，但并不总是如此。

要真正优化 JavaScript 应用的执行效率，首先需要理解什么是“任务”，以及浏览器是如何调度和执行这些任务的。只有掌握了任务的基本机制，才能更有效地识别瓶颈并采取针对性的优化措施。

## 什么是长任务

在 JavaScript 中，长任务（Long Task）是指在主线程中执行时间超过 `50 毫秒` 的任务。由于 JavaScript 是单线程运行的（即主线程负责执行 JavaScript 代码、UI 渲染、事件处理等），长任务会阻塞主线程，导致页面卡顿、掉帧、响应迟缓 等性能问题。

![alt text](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/images20250721162212.png)
JavaScript 的执行模型是基于 事件循环（Event Loop） 的。浏览器会不断地从任务队列中取出任务并执行。如果某个任务执行时间太久，比如超过 50ms，就会阻塞后续任务的执行，从而造成用户感知的延迟或卡顿。

例如：

```js
// 这个循环会阻塞主线程
for (let i = 0; i < 1e9; i++) {
  // 做一些操作
}
```

与 `JavaScript` 相关的任务主要通过以下几种方式影响网页性能：

1. 加载阶段：在页面加载期间，浏览器会下载 `JavaScript` 文件，并将解析与编译这些脚本的任务加入队列，准备后续的执行。

2. 运行阶段：在页面生命周期的其他时间，JavaScript 代码通过事件处理（如用户交互响应）、动画驱动、数据分析和收集等方式继续执行。这些操作也会以任务的形式排入队列。

需要注意的是：除了 Web Worker 等少数 API 之外，所有这些 JavaScript 任务都在主线程中执行。这意味着它们有可能阻塞页面渲染、用户输入响应等关键操作，影响整体性能表现。

## 什么是主线程

主线程是浏览器中负责执行大部分任务的核心，它运行几乎所有的 JavaScript 代码。

由于主线程是单线程的，它一次只能处理一个任务。当某个任务的执行时间超过 50 毫秒，就被称为“长任务”。其中，超过 50 毫秒的部分被称为该任务的“阻塞时间”。

在任务执行期间，浏览器无法响应用户交互。虽然短时间的阻塞通常不会被用户察觉，但如果多个耗时任务连续运行，用户在尝试点击、滚动或输入时就会明显感觉到界面迟钝或无响应。若主线程被长时间占用，甚至可能导致页面卡死或崩溃。

![alt text](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/images20250721162628.png)

> Chrome 性能分析器中所示的长任务。长任务会在任务角落显示红色三角形，并且任务的**阻塞部分会填充红色对角线条纹图案**。

为防止主线程阻塞时间过长，您可以将长任务拆分为多个较小的任务：

![20250721162659](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250721162659.png)

这一点很重要，因为当任务被拆分后，浏览器可以更快地响应更高优先级的工作，包括用户互动。之后，系统会运行剩余任务，确保您最初加入队列的工作得到完成。

![20250721162717](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250721162717.png)

在上图顶部，**由用户互动加入队列的事件处理脚本必须等待单个长任务完成才能开始，这会延迟互动发生。在这种情况下，用户可能会注意到延迟**。**在底部，事件处理脚本可以更早地开始运行，并且互动可能感觉即时**。

现在，我们已经了解了拆分任务的重要性，接下来可以了解如何在 JavaScript 中执行此操作。

## 任务管理策略

软件架构中的一个常见建议是将工作拆分为更小的函数：

```js
function saveSettings() {
  validateForm();
  showSpinner();
  saveToDatabase();
  updateUI();
  sendAnalytics();
}
```

在此示例中，有一个名为 `saveSettings()` 的函数会调用五个函数来验证表单、显示旋转图标、将数据发送到应用后端、更新界面和发送分析数据。

从概念上讲，`saveSettings()` 的架构设计得当。如果我们需要调试其中某个函数，可以遍历项目树，了解每个函数的用途。这样拆分工作有助于更轻松地浏览和维护项目。

不过，这里有一个潜在问题：JavaScript 不会将这些函数分别作为任务运行，因为它们是在 `saveSettings()` 函数中执行的。这意味着，所有五个函数都将作为一个任务运行。

![20250721165432](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250721165432.png)

在理想情况下，即使其中只有一个函数，也可能会使任务的总时长增加 50 毫秒或更多。在最糟糕的情况下，更多此类任务的运行时间可能会延长很多，尤其是在资源受限的设备上。

在本例中，`saveSettings()` 由用户点击触发，并且由于浏览器在整个函数运行完毕之前无法显示响应，因此执行此长时间任务的结果是界面运行缓慢且无响应，并且会被测量为 `Interaction to Next Paint (INP)` 较差。

### 手动推迟代码执行（

为确保面向用户的重要任务和界面响应在低优先级任务之前执行，您可以通过短暂中断工作来让出主线程，以便浏览器有机会运行更重要的任务。

开发者将任务拆分为更小任务的方法之一涉及 setTimeout()。使用此方法，您可以将函数传递给 setTimeout()。这会将回调的执行推迟到单独的任务中，即使您指定了 0 的超时时间也是如此。

```js
function saveSettings() {
  // Do critical work that is user-visible:
  validateForm();
  showSpinner();
  updateUI();

  // Defer work that isn't user-visible to a separate task:
  setTimeout(() => {
    saveToDatabase();
    sendAnalytics();
  }, 0);
}
```

这称为“让出”，最适合需要顺序运行的一系列函数。

不过，我们的代码可能并不总是按这种方式组织的。例如，您可能有大量数据需要循环处理，如果迭代次数很多，则该任务可能需要很长时间。

```js
function processData() {
  for (const item of largeDataArray) {
    // Process the individual item here.
  }
}
```

由于开发者工效学问题，在此处使用 `setTimeout()` 会出现问题，并且在嵌套 `setTimeout()` 五轮后，浏览器将开始对每个额外的 `setTimeout()` 施加至少 5 毫秒的延迟。

在让出方面，`setTimeout` 还有另一个缺点：当您使用 `setTimeout` 将代码推迟到后续任务中运行，以便让出主线程时，该任务会添加到队列的末尾。如果有其他任务正在等待，它们将在延迟执行的代码之前运行。

### 让出主线程的策略

为了避免长任务阻塞主线程，我们可以通过“让出”（_yielding_）机制将任务拆分为更小的片段。这一策略允许浏览器优先执行高优先级任务（如用户交互与渲染），从而提升页面的响应性。

过去我们通常使用 `setTimeout(fn, 0)` 来实现让出，**但它存在一些明显的缺陷：**

- 在嵌套超过 5 层后，`浏览器会强制增加最小延迟（通常 ≥5ms）`，降低效率；

- `它将任务排到宏任务队列末尾，可能被其他任务插队，延迟不可控`；

- `无法主动检测主线程负载，也不适合高频率的任务切片`。

因此，现代浏览器提供了更高效的让出手段，例如：

- `scheduler.yield()`： 可感知主线程压力的协作式让出；
- `requestIdleCallback()`： 在浏览器空闲时执行低优先级任务；
- `requestAnimationFrame()`： 分帧执行 UI 更新任务。

接下来将介绍这三种主流策略及其适用场景。

#### `scheduler.yield()`

`scheduler.yield()` 是一个专为让出浏览器中主线程而设计的 API。

它不是语言级语法或特殊结构；`scheduler.yield()` 只是一个函数，用于返回一个将在未来任务中解析的 Promise。然后，在该 Promise 解析后（在显式 .then() 链中或在异步函数中 await 该 Promise 后）链式运行的任何代码都将在该 Future 任务中运行。

在实践中：插入 `await scheduler.yield()`，该函数将在此时暂停执行并让出主线程。函数其余部分的执行（称为函数的接续）将安排在新的事件循环任务中运行。当该任务开始时，系统会解析所等待的 promise，然后函数会从上次停止的位置继续执行。

```js
async function saveSettings() {
  // Do critical work that is user-visible:
  validateForm();
  showSpinner();
  updateUI();

  // Yield to the main thread:
  await scheduler.yield();

  // Work that isn't user-visible, continued in a separate task:
  saveToDatabase();
  sendAnalytics();
}
```

![20250721173357](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250721173357.png)

函数 `saveSettings()` 的执行现在分为两个任务。因此，布局和绘制可以在任务之间运行，从而为用户提供更快的视觉响应，从现在指针互动时间大大缩短的结果来看，这一点得到了证实。

不过，与其他让出方法相比，`scheduler.yield()` 的真正优势在于其会优先执行其后续操作，这意味着，如果您在任务中途让出，当前任务的后续操作将在任何其他类似任务启动之前运行。

这样可以避免其他任务来源（例如第三方脚本中的任务）中的代码干扰代码的执行顺序。

![20250721173531](https://raw.githubusercontent.com/lcllpz/storage-imgs/main/性能优化/blogs.images20250721173531.png)

使用 `scheduler.yield()` 时，接续会从上次中断的地方继续，然后再执行其他任务。

我们还可以在任何 async 函数中对其进行 await。

例如，如果您要运行一系列作业，这些作业通常会合并为一个长任务，您可以插入 yield 来拆分该任务：

```js
async function runJobs(jobQueue) {
  for (const job of jobQueue) {
    // Run the job:
    job();

    // Yield to the main thread:
    await yieldToMain();
  }
}
```

系统会优先处理 `runJobs()` 的后续操作，但仍允许运行更高优先级的工作（例如以视觉方式响应用户输入），而无需等待可能很长的作业列表完成。

不过，这并非有效的让出方式。`scheduler.yield()` 快速且高效，但确实会产生一些开销。如果 jobQueue 中的某些作业非常短，那么开销可能会迅速累积，导致用于让出和恢复的时间比执行实际工作的时间还多。

一种方法是批处理作业，仅在上次让出足够长的时间后才在作业之间让出。常见的截止期限为 50 毫秒，目的是防止任务变成长任务，但可以根据响应速度和完成作业队列所需时间进行调整。

```js
async function runJobs(jobQueue, deadline = 50) {
  let lastYield = performance.now();

  for (const job of jobQueue) {
    // Run the job:
    job();

    // If it's been longer than the deadline, yield to the main thread:
    if (performance.now() - lastYield > deadline) {
      await yieldToMain();
      lastYield = performance.now();
    }
  }
}
```

这样一来，任务就会被拆分，以免运行时间过长，但运行程序大约每 50 毫秒才会让出主线程。

#### `requestIdleCallback()`

`requestIdleCallback()` 允许你在浏览器的空闲时间执行代码，不会打断关键任务，适合执行低优先级任务，如日志收集、懒加载、缓存处理等。

```js
function doNonCriticalWork(deadline) {
  while (deadline.timeRemaining() > 0 && tasks.length > 0) {
    doWork(tasks.shift());
  }

  if (tasks.length > 0) {
    requestIdleCallback(doNonCriticalWork);
  }
}

requestIdleCallback(doNonCriticalWork);
```

`requestIdleCallback` 可在浏览器真正空闲时执行任务，不会打断主线程，适合处理日志、懒加载等非交互型逻辑，并可通过 `deadline.didTimeout` 判断是否被强制执行。

不过，它不适用于需要及时响应的 UI 更新任务，且在浏览器高负载时可能长时间得不到调用，另外 Safari 和 Firefox 默认不支持，需使用 polyfill 兼容。

#### `requestAnimationFrame()`

requestAnimationFrame() 会在浏览器下次重绘前执行回调，执行时机为每帧的渲染前一刻，非常适合做动画、逐帧计算、视觉更新等任务。

```js
let index = 0;

function processNextChunk() {
  for (let i = 0; i < 100 && index < data.length; i++) {
    process(data[index++]);
  }

  if (index < data.length) {
    requestAnimationFrame(processNextChunk);
  }
}

requestAnimationFrame(processNextChunk);
```

`requestAnimationFrame` 与浏览器刷新节奏同步，能在每帧渲染前执行任务，非常适合处理动画、滚动等视觉更新，确保 UI 流畅且不卡顿。

但它并不适合执行后台任务，且受限于屏幕刷新率，执行频率相对固定。

## 总结

任务管理虽然具有挑战性，但它是提升网页响应速度和用户体验的关键步骤。没有单一的策略能适用于所有情况，因此需要结合多种方法灵活应对。

在管理任务时，重点应放在以下几个方面：

- 让出主线程：优先处理用户相关的关键任务；

- 使用 `scheduler.yield()`（并结合跨浏览器回退方案）、**requestAnimationFrame、requestIdleCallback**，以符合人体工学的方式分阶段执行任务并保持执行上下文；

- 尽量减少函数中的工作量：避免长任务阻塞主线程。

如需深入了解 `scheduler.yield()`、其与 `scheduler.postTask()` 的区别、以及如何基于任务优先级进行调度，请参考 [优先级任务调度 API 文档](https://developer.mozilla.org/en-US/docs/Web/API/Prioritized_Task_Scheduling_API)。

通过合理运用这些工具和策略，你可以构建出更高效的任务调度结构，确保关键交互响应优先，同时稳妥完成后台任务，从而带来更快、更流畅、更愉悦的用户体验。
