## `Expires` 的原理

`Expires` 是在 `HTTP/1.0` 中引入的响应头部，用于控制资源在客户端或代理服务器中的缓存有效期。它的工作方式是通过设置一个**绝对的过期时间**，例如：

```http
Expires: Wed, 30 Jul 2025 12:00:00 GMT
```

这表示资源在这个时间点之前，浏览器都可以直接使用缓存，不需要再次向服务器发送请求。

虽然这个机制在早期网络中起到了重要作用，但它有一些明显的局限性。首先，**它依赖客户端和服务器时间的精确同步**。如果客户端的本地时间和服务器不一致，例如比服务器时间快或者慢，就可能导致缓存提前失效或被错误地继续使用。这会影响缓存命中率和数据一致性。

其次，`Expires` **使用的是固定时间点，**不够灵活。在现代应用中，我们更希望能设置相对时间，比如“这个资源可以缓存 1 小时”或“30 分钟后过期”。但 `Expires` 无法支持这种动态的相对缓存策略，这使得它在复杂场景下难以满足需求。

正因为这些问题，HTTP/1.1 中引入了更现代的 `Cache-Control` 头部，它使用相对时间并具备更多控制粒度，从而逐渐取代了 `Expires` 的主要作用。

## `Cache-Control` 的诞生（HTTP/1.1）

`Cache-Control` 是在 HTTP/1.1 中引入的响应头，相比于早期的 `Expires`，它提供了更灵活、更强大的缓存控制能力。它的一个核心特点是使用相对时间来设置缓存时长，例如：

```http
Cache-Control: max-age=3600
```

这表示从客户端接收到响应开始，缓存可以在本地保存并使用 3600 秒（即 1 小时），期间不需要重新请求服务器。由于它基于相对时间，而不是绝对时间，因此不再依赖客户端和服务器之间的时间同步，避免了因本地时间偏差带来的缓存失效问题。

`Cache-Control` 不仅仅能控制过期时间，还能控制缓存策略，例如：

| 指令            | 含义                                     |
| --------------- | ---------------------------------------- |
| `no-cache`      | **必须向服务器重新验证缓存**             |
| `no-store`      | 完全不缓存                               |
| `private`       | 只能在私有缓存中使用（如浏览器）         |
| `public`        | 可以在公共缓存中使用（如 CDN）           |
| `max-age=秒数`  | 相对当前时间设置过期时长                 |
| `s-maxage=秒数` | 专用于共享缓存（如 CDN），覆盖 `max-age` |

通过这些指令，`Cache-Control` 实现了对缓存策略的精细化控制，不仅解决了 `Expires` 的局限性，也成为了现代 Web 开发中推荐使用的缓存机制。

## `Expires` 和 `Cache-Control` 的区别对比

| 特性           | `Expires`             | `Cache-Control`        |
| -------------- | --------------------- | ---------------------- |
| 引入版本       | HTTP/1.0              | HTTP/1.1               |
| 时间类型       | 绝对时间              | 相对时间               |
| 可控性         | 只能指定过期时间      | 控制粒度更细、功能更强 |
| 受系统时间影响 | 是                    | 否（相对时间）         |
| 是否推荐       | ❌ 不推荐（向后兼容） | ✅ 推荐使用            |

## 总结

虽然 `Cache-Control` 是 HTTP/1.1 中更现代且灵活的缓存控制方式，但仍然保留了 `Expires`，主要是为了兼容旧的 HTTP/1.0 客户端和代理服务器。两者可以同时存在，当出现冲突时，HTTP/1.1 客户端会优先使用 `Cache-Control`。虽然不是必须都写，但为了更好的兼容性，实际部署中通常建议两个都设置。
